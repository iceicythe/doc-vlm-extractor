# DSPy 指令优化报告 —— 跨域 WildReceipt（flat 模式）

> 日期：2026-09-19 ｜ 状态：**已完成**（含三组归因对照）
> 成本：全量优化 ¥0.46 + 三组评测 ¥0.36 ≈ **¥0.82**

## 0. 一句话结论

**DSPy 见效了（跨域 F1 0.4408 → 0.7085），但功劳不在「把措辞改得更漂亮」，而在于它自己发现了 prompt 的结构性缺陷：手写 prompt 只要求抽 3 个字段，而真值平均有 6.43 个。**

三组对照把归因钉死了：

| 组 | prompt | 跨域 F1（留出 100 条） |
|---|---|---:|
| A | 手写 3 字段（原 baseline） | 0.4408 |
| B | **手写 8 字段**（机械补清单，其余一字不动） | **0.7085** |
| C | GEPA 优化版 | 0.6830 |

⇒ **补字段 = +26.8pt；GEPA 的措辞建议 = −2.6pt。**
GEPA 找到了对的问题，但给出的具体规则**反而略微拖后腿** —— 连它自己选候选的那 40 条验证集上，
B（0.7734）也高于 C（0.7447）。**这是典型的过拟合小验证集。**

**第二个结论（同样重要）：这条"prompt 缺陷"解释不了本地小模型。**
把同一个 8 字段 prompt 给本地 ②/③ 跑（§3.5）：召回同样翻倍（0.23→0.50、0.21→0.42），
但精确率同时塌掉，幻觉率飙到 **0.59 / 0.73** —— 它照着 8 个字段名逐条填空、抽不出来就编，
③ 平均每张多编 1.6 个字段。

⇒ 换成「天花板达成率」看就清楚了：**prompt 只决定天花板高度，能接近多少由模型能力决定。**

| 档 | 3 字段（天花板 0.4168） | 8 字段（天花板 0.9907） |
|---|---:|---:|
| ② 2B 零样本 | 55.2% | 50.1% |
| ③ 2B SFT | 50.0% | 42.2% |
| ⑤ API | 75.7% | 72.7% |

同一档位换 prompt，达成率几乎不动；**跨档位差异（50% vs 73%）才是真差距**。

## 1. 这个模块要回答的问题

不是「再加一个模块让简历多一行」，而是回答一个已经存在的疑问：

> **不改权重、纯靠自动优化 prompt，能走到哪一步？**

顺带修正一个常见误解：**DSPy 对已经微调过的档位没有意义**。
③ 档的 prompt 已被内化进权重（硬证据：知识注入对 ③ 档只改动 **1 处**），
再去改推理 prompt 反而制造训练/推理不匹配。所以 DSPy 只对 **② 零样本 / ⑤ API** 有意义。

## 2. 口径设计（这部分比结果更重要）

### 2.1 数据切分：优化过程不碰评测集

| 用途 | 数据范围 | 条数 |
|---|---|---:|
| **评测集（冻结不动）** | `wildreceipt_test.jsonl` 第 **1–100** 条 | 100 |
| trainset（GEPA 反思用） | 第 101–124 条 | 24 |
| valset（GEPA 选候选用） | 第 125–164 条 | 40 |

评测集与 ⑤ API 档**完全相同**（已逐条按 basename 校验），数字可直接比。
trainset/valset 从第 101 条起切 —— **优化过程从未见过评测集**。

### 2.2 优化器：GEPA，且只改 instruction

`dspy.GEPA`（反射式指令优化器）。选它的原因：它带「看失败案例 → 反思 → 改指令」的循环，
而 VLM 场景**不能塞带图 demo**（token 会爆炸），所以只让它改 instruction。

metric 直接复用 `evaluate.py` 的打分函数（`score_one` + `prf`），并返回**具体到字段的反馈文本**：

```
漏抽 3 个字段：['store_addr', 'tax', 'subtotal'] 值错误 1 处：total 应为 '$60.44' 实为 '60.44'
```

只回一个 F1 数字，反思器只能瞎猜；告诉它「漏了哪几个字段」，它才能对症下药 ——
**这次它做对的就是这件事**。

### 2.3 最终对比走同一个管道

dspy 发给模型的 prompt ≠ instruction 原文（它还会包上字段名与格式要求），
两边分数不可混谈。所以：**dspy 内部分数只用于优化过程，正式数字一律由 `evaluate_api.py` 产出。**

## 3. 结果

### 3.1 优化过程（valset 40 条，budget=200）

| | val F1 |
|---|---:|
| baseline（手写 3 字段） | 0.5205 |
| **GEPA 优化后** | **0.7490** |
| Δ | **+0.2286** |

用时 **80 秒**、326 次 VLM 调用 + 6 次反思调用、¥0.46。
GEPA 在第 2 轮就找到本轮的全局最优，之后两轮都是 `Reflective mutation did not propose a new candidate`
—— 反思器**已收敛，不再产出新候选**（4 轮用完了 200 次预算）。

分数轨迹：`0.5205 → 0.6413 → 0.7490 → 0.7490 → 0.7490`

### 3.2 三组归因对照（核心）

**同一个 100 条留出评测集、同一个管道、唯一变量是 prompt：**

| 组 | F1 | P | R | 幻觉率 |
|---|---:|---:|---:|---:|
| A 手写 3 字段 | 0.4408 | 0.7302 | 0.3157 | 0.090 |
| **B 手写 8 字段** | **0.7085** | 0.6973 | **0.7201** | **0.210** |
| C GEPA 优化版 | 0.6830 | 0.6712 | 0.6952 | 0.250 |

**同一批数据在 40 条验证集上的复现（用来验证「过拟合」这个归因）：**

| 组 | F1 | P | R | 幻觉率 |
|---|---:|---:|---:|---:|
| A 手写 3 字段 | 0.5191 | 0.8333 | 0.3770 | 0.100 |
| **B 手写 8 字段** | **0.7734** | 0.7615 | 0.7857 | **0.175** |
| C GEPA 优化版 | 0.7447 | 0.7212 | 0.7698 | 0.250 |

⇒ **两个数据集上都是 B > C。** 这个一致性很关键：
GEPA 是在那 40 条 valset 上**按分数选出来的**，却仍输给「人工机械补字段」——
说明它多写的那部分规则是**过拟合**，不是有效优化。

### 3.3 GEPA 写了什么（含一次自我修正 —— 别记错版本）

**⚠️ 版本更正**：早前一版报告把「去空格」「塞 tips」记在了最终产物头上。
翻 `outputs/dspy_full.log` 逐轮比对后确认，那其实是**迭代 1 的中间候选**，不是导出的东西：

| 迭代 | 候选指令的特征 | val F1 |
|---|---|---:|
| 1 | 把 `store_name` 规范化为全大写去标点（`VJ'S RANGOON` → `VIJSRANGOU`）；日期去掉星期前缀（`WED JULY 20,2011` → `JULY202011`）；字段清单里多塞 `tips` | 0.6413 |
| **2（导出这版）** | **这些全被它自己删掉了** —— 最终版明写「字段值必须严格保留图片中的原始写法，**包括大小写、空格、标点**」；清单回到 8 个字段、无 `tips` | **0.7490** |

⇒ 迭代 1 那版规则确实是有害的（值与真值不等），**但它自己修掉了**。
导出的 `outputs/dspy_optimized_flat.txt` 里没有任何"去空格"或 `tips`。
（这条更正重要：面试官真去读那个文件，会发现它写的和旧描述相反。）

**那 C 为什么还是输给 B（留出集 −2.6pt）？** 按字段拆开看，损失是**均匀的、无单点崩溃**：

| 字段 | B tp/fp/fn | C tp/fp/fn | Δtp |
|---|---|---|---:|
| store_name | 62/38/38 | 64/36/36 | +2 |
| store_addr | 17/74/64 | 15/76/66 | −2 |
| **tel** | **51/16/14** | **44/26/21** | **−7** |
| date | 63/15/13 | 60/18/16 | −3 |
| time | 61/17/15 | 61/17/15 | 0 |
| subtotal | 65/15/12 | 63/16/14 | −2 |
| tax | 62/11/8 | 59/14/11 | −3 |
| total | 82/15/10 | 81/16/11 | −1 |
| tips | 0/0/6 | 0/0/6 | 0 |
| **合计** | **463/201/180** | **447/219/196** | **−16** |

真实原因是它替换上来的那条**激进召回规则**——「必须逐项检查收据的顶部、底部、页脚、边角、
细小字区域」「只要图中出现，就应提取」。方向跟"补字段"一致，但**已经过量**：
FP 从 201 涨到 219，损失最大的一块是 `tel`（−7 tp / +10 fp，电话号最容易在边角处误读）。
⇒ **同一条规则在"漏抽 4 个字段"时是解药，在字段已补齐后就成了过拟合。**

**唯一做对的、也是唯一重要的**：它从失败反馈里读出了「漏抽 store_addr / tax / subtotal」，
判断这是**字段清单缺失**而非模型看不清，然后补齐 —— 一步掀掉天花板。

### 3.4 这个发现改写了「跨域不能用」的结论

| | 数值 |
|---|---:|
| 手写 flat prompt 点名的字段 | 3 |
| 真值字段总数（100 条） | **643**（平均 6.43） |
| 其中被 prompt 点名 | **268** |
| ⇒ recall 天花板 | **268 / 643 = 0.4168** |
| ⑤ 档原跨域 F1 / recall | 0.4408 / **0.3157** = 天花板的 **75.7%** |
| 补齐 8 字段后 | 天花板 **637/643 = 0.9907**；实得 F1 **0.7085** / recall **0.7201** = 72.7% |

⚠️ 更正：旧文写「0.3157 **已贴着天花板**」是夸大了 —— 实际只到天花板的 **75.7%**，
还有 24pt 空间，这也正是补字段能涨 +26.8pt 的原因。
（剩余 6 个字段 `tips` 未被点名，占 6%，所以新天花板是 0.9907 而不是 1.0。）

**三条档位横向看，天花板达成率几乎只由模型决定、与 prompt 无关**：

| 档 | 3 字段：R / 天花板 0.4168 | 8 字段：R / 天花板 0.9907 | 达成率变化 |
|---|---:|---:|---:|
| ② 2B 零样本 | 0.2302 → **55.2%** | 0.4961 → **50.1%** | −5.1pt |
| ③ 2B SFT | 0.2084 → **50.0%** | 0.4184 → **42.2%** | −7.8pt |
| ⑤ API | 0.3157 → **75.7%** | 0.7201 → **72.7%** | −3.0pt |

⇒ **prompt 只决定天花板高度；能不能接近天花板，是模型能力的事。**
本地两档无论怎么改 prompt 都卡在天花板的一半左右，而 API 稳定在 3/4 ——
**这一格 4–5 档的差距是感知能力，不是 prompt。**

**⑤ 档跨域那格上不去，主因不是「模型看不清」，而是「prompt 压根没让它抽那些字段」。**
换 prompt 后 F1 直接翻了 1.6 倍、幻觉率反而从 0.25 回落（B 组 0.210），
这是本报告最有价值的单条结论。

⚠️ **这条结论不能直接外推到本地 ②/③ 档。原计划用「本地也换 8 字段 prompt」来验证，
对照已经跑完了 —— 结论比预期更干净，见下。**

### 3.5 本地 ②/③ 也换 8 字段 prompt：对照已跑（¥0，本地推理）

同一批 100 条评测集，唯一变量是 prompt：

| 档 | prompt | F1 | P | R | 幻觉率 |
|---|---|---:|---:|---:|---:|
| ② 2B 零样本 | 3 字段 | 0.3190 | 0.5193 | 0.2302 | 0.16 |
| ② 2B 零样本 | **8 字段** | **0.4691** | 0.4449 | 0.4961 | **0.59** |
| ③ 2B SFT | 3 字段 | 0.2842 | 0.4467 | 0.2084 | 0.28 |
| ③ 2B SFT | **8 字段** | **0.3752** | 0.3401 | 0.4184 | **0.73** |
| ⑤ API | 3 → 8 字段 | 0.4408 → **0.7085** | 0.7302 → 0.6973 | 0.3157 → **0.7201** | 0.09 → 0.21 |

三件事：

1. **本地档确实也涨了，但只拿到 API 的一半不到** —— ② +15.0pt、③ +9.1pt，而 ⑤ +26.8pt。
2. **召回翻倍是真的**：② 0.2302 → 0.4961、③ 0.2084 → 0.4184（都是约 2.1×）
   ⇒ **prompt 天花板对本地档同样存在**，老口径「本地跨域差」确实有一部分是 prompt 造成的。
3. **但精确率同时塌了**（② 0.5193 → 0.4449、③ 0.4467 → 0.3401），
   幻觉率从 0.16 / 0.28 飙到 **0.59 / 0.73**。

**机制很清楚：本地 2B 把「找不到的字段可省略」这条指令彻底忽略了。**
它照着 8 个字段名逐条填空，抽不出来就编：

| | 平均输出键数 | 真值平均字段数 | 幻觉键占输出比 |
|---|---:|---:|---:|
| ⑤ API 8 字段 | **6.64** | 6.43 | 30 / 664 = **4.5%** |
| ② 零样本 8 字段 | **7.84** | 6.43 | 95 / 784 = 12.1% |
| ③ SFT 8 字段 | **8.0** | 6.43 | 154 / 800 = **19.3%** |

> **口径**：解析后 JSON 里**命中已知 8 个字段名**的键数 / 图。
> ⚠️ 2026-09-19 复核：本表 ② 行原先写的 7.5 / 752 **不可复现**，已更正为 7.84 / 784
> （③ 行 8.0 与 API 行 6.6 复核一致）。后续凡"平均键数"一律用 `scripts/_analyze_fields.py` 的口径，别手算。

③ 每张收据**固定吐 8 个键**（8.0/条），而真值平均只有 6.43 个 —— 也就是平均每张多编 1.6 个。
最极端的两格：`subtotal` 在 23 张本就没有它的收据上，② 编了 **23 次（100%）**；
`tax` 在 30 张上编了 27 次（**90%**）。

⇒ **本地档换 prompt 后，错误形态从「该抽的没抽」变成了「不该抽的也抽」。**
它不缺字段清单，缺的是**判断这张收据到底有没有这个字段**的能力 —— 这正是感知层的事。

⚠️ **一条口径提醒**：③ SFT 是在同域 **schema** 格式上微调的，8 字段 flat prompt 本来就在
训练分布之外，所以 ③ 的 8 字段数字带一项额外的不利因素。**要解释跨域能力，② 那一行更干净。**

### 3.6 那再加强指令呢？—— 又跑了一次，答案还是「不能」

§3.5 把问题定位到「不缺字段清单，缺的是判断这张收据有没有这个字段」。
顺着这个思路最自然的下一步是**把指令写狠**：既然它老编不存在的字段，就明确禁止它这么做。

`outputs/prompt_manual_8f_strict.txt`（161 → **272 字符**）与 §3.5 用的 8 字段 prompt
**只差这一处**：把「找不到的字段可省略。」换成强规则段（只输出真实看到的字段 /
不存在就完全不输出该键名 / 不要 null、空串或占位符 / 严禁按常理推测编造 / 宁缺毋滥）。
**字段清单句与输出格式句逐字未动** ⇒ 严格单变量。

| 档 | prompt | F1 | P | R | 幻觉率 |
|---|---|---:|---:|---:|---:|
| ② 2B 零样本 | 8 字段 | 0.4691 | 0.4449 | 0.4961 | 0.59 |
| ② 2B 零样本 | 8 字段 **＋强指令** | 0.4556（**−1.4pt**） | 0.4344 | 0.4790 | **0.54** |
| ③ 2B SFT | 8 字段 | 0.3752 | 0.3401 | 0.4184 | 0.73 |
| ③ 2B SFT | 8 字段 **＋强指令** | 0.3654（**−1.0pt**） | 0.3333 | 0.4044 | **0.71** |

**幻觉率只降 2–5 个点，F1 反而掉 1 个点以上。** 拆到 tp/fp 上看更清楚：

| 档 | tp | fp | 平均输出键数（解析后 JSON 键数口径） |
|---|---:|---:|---:|
| ② 8 字段 | 319 | 398 | 7.84 |
| ② ＋强指令 | **308（−11）** | 401（**＋3**） | 7.92 |
| ③ 8 字段 | 269 | 522 | 8.00 |
| ③ ＋强指令 | **260（−9）** | 520（−2） | 8.00 |

**强指令几乎没删掉任何一个编造字段，却把一批本来抽对的字段一起劝退了。**
逐字段看「无中生有」次数（真值里没有该键、模型却输出了它）：

| 字段 | ② 基线 → 强指令 | ③ 基线 → 强指令 |
|---|---|---|
| subtotal | 23 → 20 | 23 → 23 |
| tax | 27 → 23 | 29 → **30** |
| total | 8 → 8 | 8 → 8 |
| store_addr | 15 → 14 | 19 → 19 |

③ 的 `tax` 甚至**多编了一个**。而 `total` 那一格，③ 的 tp 从 33 掉到 28、fp 从 67 涨到 72
—— 指令没有压住幻觉，只是让它更不敢输出。**输出键数几乎不动（7.84 → 7.92、8.00 → 8.00）**，
这一条本身就说明：它压根没觉得自己在编。

原因说出来很简单：**模型不是在「知道该省却硬要编」，它是真心认为那些字段就在图上。**
既然它"看到了"，任何「不存在就别输出」的措辞都无从触发。

⇒ 这是 §3.5 结论的**第二次独立验证**：**跨域的瓶颈在感知层，不在指令措辞层。**
要真正压住幻觉得从数据 / 感知侧入手（更多真实收据、更高分辨率输入、字段级裁剪），
而不是继续调 prompt —— 这也是本项目后续没有在 prompt 上再投入的原因。

> 数据：`outputs/eval_wr_{zero,sft}_8f_strict.json`；
> 逐字段拆解脚本：`python scripts/_analyze_fields.py base=<A>_preds.jsonl strict=<B>_preds.jsonl`
> （口径与 `evaluate.py` 一致：直接复用 `parse_json` / `flatten_flat`，不另写一套打分）。
> 幻觉率沿用 `evaluate.py` 的 `hallucination_rate` 口径。

## 4. 三组对照是怎么做干净的

| 组 | prompt 文件 | 隔离出的变量 |
|---|---|---|
| A | `evaluate.py` 内置 `PROMPTS["flat"]` | — |
| B | `outputs/prompt_manual_8f.txt` | **补字段**的贡献 |
| C | `outputs/dspy_optimized_flat.txt` | 补字段 **+** 措辞/规则 |

A 与 B 逐字比对过：**只差字段清单，其余一字不动**（同一句话模板、同样的
"字段名用英文，值保留图中原文。找不到的字段可省略。只输出 JSON…"）。
所以 B−A 就是纯粹的「补字段」效应。

B 组字段清单覆盖了真值的 8 个主要键（`store_name / store_addr / tel / date /
time / subtotal / tax / total`）。真值第 9 个键 `tips` 只在 6% 的评测样本里出现，未纳入。

## 5. 踩坑记录（4 条，第 4 条最值钱）

### 5.1 `from __future__ import annotations` 会让 dspy 直接崩

```
ValueError: Field types must be types, but received: ForwardRef('dspy.Image')
```
它把 `dspy.Image` 这类注解变成字符串，dspy 解析 Signature 时拿不到真实类型。
**这个文件里绝不能加这一行。**

### 5.2 GEPA 的 log_dir 复用会导致状态错位

GEPA 见到已有 run dir 会**静默加载旧状态续跑**。smoke 用 8 条 valset、
全量用 40 条，状态错位后在 `_evaluate_programs_on_valset` 抛 `IndexError`
（报错点离真因隔了好几层）。现在 log_dir 带时间戳，每次都是干净状态。

### 5.3 litellm 启动会去 GitHub 拉价格表：41s → 2.7s

国内网络必然超时并重试 3 次。设 `LITELLM_LOCAL_MODEL_COST_MAP=True` 用本地备份：

| | 导入耗时 |
|---|---:|
| 默认 | **41.0 s** |
| 置真 | **2.7 s** |

### 5.4 ⭐ 余额耗尽被静默降级成「一个正常结果」

这是本项目第三次踩到**同一族**问题：

| # | 位置 | 表现 |
|---|---|---|
| 1 | `evaluate_api.py` | 空响应被 `content or ""` 当成有效结果 → F1 被悄悄压低 9.2pt |
| 2 | `evaluate_api.py` | `load_dotenv()` 定义了但没接线 → 明明填了 key 却报未设置 |
| 3 | **GEPA 这一轮** | 余额耗尽后**空转完 200 轮**，把 baseline 原文当优化结果写盘，**退出码 0、Δ=0、不报任何错** |

**共同点：失败被降级成「一个看起来正常的结果」。**

第 3 条的危害在于：只看最后三行输出（`Δ +0.0000`），结论会写成
**「DSPy 优化无效」** —— 而事实是**优化根本没跑成**。

已加两道闸（均已实测）：

1. **闸门 1 · preflight**：开跑前发一次极便宜的请求确认端点可用。余额/鉴权不对立刻退出
   （退出码 1）。**已在余额耗尽状态下实测：秒退、不再空转 20 分钟。**
2. **闸门 2 · 结果自检**：若最优指令与基线**一字不差**，打印醒目警告并返回码 2 ——
   明确区分「ΔF1=0 因为没跑成」和「ΔF1=0 因为优化无效」。
