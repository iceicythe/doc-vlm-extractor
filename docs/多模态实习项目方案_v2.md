## 三、技术选型

### 锁定方案

```
基座：unsloth/Qwen3-VL-2B-Instruct-unsloth-bnb-4bit
方法：QLoRA（全层 LoRA），Unsloth FastVisionModel
图像：384px（必须对齐 32 像素网格，视觉 token ≈ (H/32)×(W/32)）
LoRA：r=16~32，vision + language + attention + MLP 全开
训练：batch=1, grad_accum=8, 梯度检查点开启
```

### 为什么是 2B 而不是 4B

| 维度 | 2B | 4B |
|---|---|---|
| 官方 BF16 推理最低显存 | 5GB（推荐 8GB） | **9GB（推荐 12GB）** |
| SFT 峰值估算 | 3–5GB | 6–8GB（贴边） |
| **DPO 峰值估算** | **4–6GB** | 大概率 OOM |
| 结构化提取的表现差异 | — | 小于"数据质量 + 分辨率"带来的差异 |

**决定性理由：DPO 环节。** DPO 序列翻倍，4B 在 8GB 上没有腾挪空间。而 DPO 是"后训练"叙事的承载者，不能让它成为瓶颈。

### 三个易踩的坑

1. **选 Instruct，不要 Thinking。** Thinking 版输出思维链，token 数翻几倍，对"直接输出 JSON"是纯负担。
2. **分辨率对齐 32 像素网格。** 512px 即 256 视觉 token。**分辨率是显存第一杀手，比模型大小影响更大。**
3. **OOM 处理顺序**：降分辨率 → 减 LoRA rank → 最后才冻结 vision 层。冻结视觉层会直接削弱"看得准"的能力。

### 何时升级到 4B

- 第 3 周 2B 对比表出来后，**与 API 的 F1 差距仍 > 0.2**；
- 或失败分析显示瓶颈是**"认字不准"（视觉）** 而非 **"格式不对"（语言）**。

### 备选

| 场景 | 方案 |
|---|---|
| Qwen3-VL 架构在 8GB 出兼容问题 | 退 **Qwen2.5-VL-3B**（Unsloth 支持成熟、社区案例最多） |
| DPO 显存仍不够 | 换 **ORPO / SimPO**（无需 reference model，显存 = SFT；ORPO 还能省一次训练） |

## 四、显存预算与训练约束

### 逐模块账（Qwen3-VL-2B / QLoRA / 384px）

| 模块 | 峰值估算 | 判断 |
|---|---|---|
| SFT | 3–5GB | 宽裕 |
| **DPO** | **4–6GB** | 可行，但余量小 |
| DSPy prompt 优化 | 仅推理 ~2–3GB | 无压力 |

### DPO 的关键技术点

**必须用 Unsloth。** Unsloth 的 DPO 支持 `ref_model=None`，通过**禁用 LoRA adapter** 来充当 reference model，**不额外加载一份权重**。

```python
from trl import DPOTrainer
dpo_trainer = DPOTrainer(
    model=model,
    ref_model=None,          # Unsloth handles this
    train_dataset=dpo_dataset,
    tokenizer=tokenizer,
    args=training_args,
    beta=0.1,
)
```

> ❌ **绝不能换 LLaMA-Factory 或裸 TRL 做 DPO** —— 它们会加载两份模型权重，8GB 必炸。

### DPO 的五个前提

1. 必须 Unsloth（`ref_model=None`）
2. 图像 384px
3. **`max_length` 卡死**（chosen/rejected 是短 JSON，约 512 token，别用默认长序列）
4. batch=1 + grad_accum，开梯度检查点
5. 训练时关掉浏览器等占显存程序

### 时间预算（独立于显存）

| 项 | 粗估 |
|---|---|
| SFT 单次（2000 条 × 3 epoch） | 25 分钟 – 1 小时 |
| DPO 单次（序列翻倍） | 1–2 小时 |
| DPO 偏好数据采样（500 图 × 8 输出 = 4000 次生成） | **2–4 小时** |
| 消融实验（6–9 次训练） | **10–20 小时** |

> **显存够 ≠ 时间够。** 两个独立约束，消融实验的时间成本必须提前排进计划。

## 五、数据管线（本项目最值钱的资产）

> JD 第 2 条要求"研究和**落地**"。管线的含金量在于：**它回答的是"没有标注数据时怎么办"**——这正是企业真实困境。

### 5.1 数据源

| 类别 | 数据集 | 用途 |
|---|---|---|
| 英文真实 | **WildReceipt**（1765 张收据，25 类 key-value，PaddleOCR 官方直链，有 SDMGR 基线数字可引用） | 训练 + 测试 |
| 英文真实 | **CORD**（1000 张小票，字段级 JSON，HuggingFace `naver-clova-ix/cord-v2`） | 训练 + 测试 |
| 英文真实 | **FUNSD**（199 张表单，`nielsr/funsd`） | **零样本泛化测试（不参与训练）** |
| **中文合成** | **自建渲染管线**（工程单据风格，1000–2000 张） | 主力 |
| 真实补充 | **20–50 张真实工程单据/造价单照片** | **真实 gap 评估（关键）** |

> ⚠️ 中文公开集 **EPHOIE** 需申请 + 提交论文证明，学生拿不到。中文场景靠自建合成覆盖。
> ❌ 不用 DocVQA（QA 型而非提取型）；不碰 PubTabNet（50 万张，8GB 训不完）。

### 5.2 合成数据设计（核心工作量）

**要做的全部事情**（v1 里被压缩成"占 50% 工作量"一句话）：

1. **schema 设计** —— 决定后面所有指标，改一次全重来
2. **HTML 模板** —— 要有工程单据的样子，不能像小票
3. **随机化渲染** —— 表头、字段名、金额、日期、单位
4. **退化管线**（参考公开先例的参数清单）：
   - 几何：旋转 ±6°、透视畸变、轻微倾斜
   - 光学：高斯模糊、运动模糊、亮度/对比度变化、阴影与高光
   - 噪声：传感器噪声、JPEG 重压缩（质量 15–100，权重偏向手机档 65–90）
   - 物理：折痕、污渍、雨滴
   - **印章合成**（工程单据特有）
5. **中文字体** —— 字体授权 + 字形缺失处理（比英文麻烦得多）
6. **Ground truth 生成与 schema 对齐**
7. **API 蒸馏标注** + 人工抽检 100 张算一致性
8. 输出对齐 32 像素网格，resize 到 384px

### 5.3 蒸馏标注与噪声控制

- 用便宜 API（DeepSeek / GLM-flash 级）做标注
- **人工抽检 100 张，报告一致性（Kappa 系数）**
- **记录 API 标注犯的错及处理方式** ← 这是企业真会踩的坑，第一手经验含金量高

### 5.4 数据划分

```
训练集：WildReceipt + CORD + 合成数据
验证集：各源留出
测试集：CORD test + WildReceipt test + 合成留出集（分集报告！）
零样本：FUNSD（不用中文合成，测跨域泛化）
真实 gap：20–50 张真实工程单据（人工定性评估）
```

## 六、评测设计

### 6.1 指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| **字段级 F1** | 按各数据集自己的 schema 算 | **必须分集报告，不可跨集平均** |
| JSON 合法率 | 输出可被 `json.loads` 解析的比例 | 输出约束的有效性 |
| **幻觉率** | 输出了 schema/图中不存在的字段的比例 | DPO reward 的惩罚项 |
| ANLS | 文本相似度（归一化编辑距离） | 与字段 F1 互补 |
| 单张推理成本 | 元/张（含能耗折算） | 落地语言的硬指标 |
| 单张延迟 | 秒/张 | — |

> ⚠️ **v1 的错误修正**：CORD（`menu.nm/price`）、WildReceipt（25 类 key-value）、自建合成（工程单据字段）**三套 schema 无交集**，合成一个总 F1 是没有意义的数字。**分集报告**，再用统一的可迁移指标做横向对照。

### 6.2 五档对比表（简历最硬的一行）

```
① PaddleOCR + 规则基线
② Qwen3-VL-2B 零样本
③ Qwen3-VL-2B 微调后          ← 本项目主交付
④ Qwen3-VL-8B 4bit 零样本     ← 关键对照
⑤ GPT-4o 级 API（上限参照）
```

> **④ 的意义**：8B 4bit **推理**在 8GB 上可行（4bit 约 5–6GB，不训练）。
> 若 **③ > ④** 成立 —— **"我的 2B 微调后 ＞ 8B 零样本"** —— 这是整个项目最强的招聘信号：证明你会用数据和微调换模型规模，而不只是会调参。**且不额外花钱、不用训练，只多跑一遍推理。**

### 6.3 消融实验（挑 2–3 个）

| 消融项 | 档位 | 产出 |
|---|---|---|
| **图像分辨率** | 384 / 512 / 768 | 精度–显存–延迟曲线（必做） |
| **LoRA 打在哪** | 仅 language vs 全层 | 对文档提取，视觉层该不该训（有争议，你的数据给答案） |
| **合成数据比例** | 纯真实 / 纯合成 / 混合 | **合成路线的核心论证** |
| 训练数据量 | 25% / 50% / 100% | 数据效率曲线（企业最关心） |

### 6.4 失败分析（零成本，最优先做）

把测试集错例分类：

| 错误类型 | 归因层 |
|---|---|
| 认错字 / 数字看错 | 视觉 |
| 字段串位（金额填到数量） | 结构化 |
| 幻觉（输出图中不存在的字段） | 语言 |
| JSON 格式崩 | 输出约束 |
| 长尾（倾斜 / 模糊 / 印章遮挡） | 数据 |

每类给**占比 + 2–3 个真实例子 + 归因**。

**三重价值**：① 博客最吸粉 ② 面试最能讲 ③ **直接指导下一步**（瓶颈在视觉→提分辨率/升 4B；在格式→改数据）。

## 七、深度抓手（范围收敛后必须变深）

> **项目薄 ≠ 功能少，而是没有"发现"。加深的唯一路径是：不加功能，只加对照与分析。**

| # | 抓手 | 成本 | 说明 |
|---|---|---|---|
| 1 | **失败分析** | 零 | 见 6.4，最先做 |
| 2 | **消融实验** | 低（重跑训练） | 见 6.3 |
| 3 | **成本–精度 Pareto + 回本点** | 零 | 见下 |
| 4 | **反直觉发现** | 被动等结果 | 见下 |
| 5 | **数据管线显性化** | 零 | 见第五章 |

### 3. 成本–精度 Pareto 图

横轴单张成本（对数），纵轴字段 F1，把五个方案点上去。然后说企业听得懂的话：

> **F1 达到 API 大模型 XX% 的水平下，单张成本降低 XX 倍。**

**加深版**：成本算细 —— API 费 + 本地推理时间折算 + 训练一次性 GPU 成本 + **人工标注成本**，算总拥有成本，给出 **"数据量 > N 时自建方案回本"的临界点**。

### 4. 反直觉发现（跑完实验主动去找）

- 合成数据加到 2000 张，收益还在涨还是已饱和？
- **合成测试集 F1 vs 真实照片 F1，gap 多大？**（公开先例明确承认未测——**你测了就更完整**）
- 2B + 好数据 vs 8B + 差数据，谁赢？
- 训练退化强度是否存在最优值（加太狠反而伤性能）？

### 5. 数据管线显性化

schema 迭代史 / 退化参数依据 / 蒸馏标注噪声控制（含 Kappa）/ 中文字体坑。

### 自检标准

> **面试官连问三个"为什么"，能否每个都拿数字答？**
> 为什么用 2B 不用 4B？→ 消融数据
> 为什么合成数据有用？→ 混合比例实验
> 为什么比 OCR+规则好？→ Pareto 图 + 回本点

## 八、DPO 后训练

### 为什么是 DPO 而不是 GRPO

在线 RL 每步要采样多个回答，KV cache 显存峰值高、无 vLLM 采样慢（**且 vLLM 在 Windows 上不支持**）、调参坑多。**DPO 是离线训练，显存与 SFT 相当。**

### 流程

1. **设计可验证 reward**：`JSON 合法性 + 字段级 F1 − 幻觉惩罚`
2. **构造偏好数据**：SFT 后模型对每张验证图采样 4–8 个输出（temperature 0.7–1.0），reward 打分，最高分作 chosen、最低分作 rejected；**分差 < 阈值的对丢弃**
3. **DPO 训练**：Unsloth（`ref_model=None`）+ QLoRA，配置同 SFT
4. **评测**：base → SFT → DPO 三档对比（字段 F1 / JSON 合法率 / 幻觉率）

### 叙事洞（必须提前补）

**DPO 严格说不是强化学习**，是 RLHF 的免奖励模型闭式近似。面试官若懂行会追问：

- DPO 为什么能绕过奖励模型？
- 为什么在 8GB 上比 GRPO 现实？
- **牺牲了什么？** —— 不能在线探索，只能从离线偏好对中学习

### 常见坑

- 偏好对差距太小（分差 < 阈值 → 丢弃）
- **DPO 后 JSON 合法率可能不升反降**（reward 权重需调）—— 踩过并解决，面试可讲的更多

## 九、DSPy prompt 优化

### 定位

**不是外挂模块，而是贯穿数据管线与评测的横轴。**（DSPy 官方论文 *BetterTogether: Fine-Tuning + Prompt Opt.* 即持此立场）

### 技术事实（已核实）

- **DSPy 3.3 原生支持多模态**：`dspy.Image` 是内置类型，支持本地路径 / URL / PIL
- **优化器用 GEPA**（反思式进化，2025-07），经典款 MIPROv2 亦可
- **成本参考**：官方实测 GEPA 优化 200 样本 = **$2.18**；本项目估算 10–30 元
- **优化器模型必须能看图**（GEPA 要靠分析失败案例的图片来反思改写 prompt）

### 三个融入接口

**① metric 复用** —— 主项目的字段 F1 函数直接作为 DSPy 的 metric，**不要另写一套评测**。

**② 优化结果反哺数据管线** —— 用 GEPA 搜出的最优 prompt 作为**蒸馏标注模板 / 微调的指令模板**。让 prompt 优化**有产出**，而不是一个孤零零的数字。

**③ 2×3 联合矩阵（核心结论产出）**：

```
                 手写 prompt    自动优化 prompt      Δ
API 大模型           ?              ?              ?
2B 零样本            ?              ?              ?
2B 微调后            ?              ?              ?
```

> **核心问题：微调之后，prompt 优化的收益还剩多少？**
> Δ≈0 → "微调已吃掉 prompt 优化空间，企业不必重复投入"
> Δ 显著 → "两者互补"
> **无论哪个结果都是可报告的发现。**

### 三个坑

1. 优化器模型必须能看图 → 用多模态 API
2. DSPy 多模态走 OpenAI 兼容的 `image_url` block → 接国产 API 需确认其兼容层支持
3. 若用本地 Qwen3-VL 当执行器 → 需起一个 OpenAI 兼容服务（vLLM 在 Windows 不可用，改用 LM Studio / Ollama）

## 十一、风险与 Plan B

### 风险 1：PaddleOCR + 规则可能反超（最大的隐性风险）

**在 CORD / WildReceipt 这类强格式字段上（金额、日期、发票号），规则抽取的准确率很高，VLM 微调后未必能大幅超过，甚至可能输。**

若输了，简历上"F1 提升至 0.XX"写不出来。

**Plan B 叙事（大概率用得上）**：不比绝对 F1，改比 ——

- **同等精度下的成本**（自建方案远低于按张计费的 API）
- **schema 迁移成本**（换一个字段：规则方案要改代码重测，本方案只需改 prompt）

企业真实的决策依据是这两条，不是小数点后两位。

### 风险 2：合成数据的真实 gap

FUNSD 测的是"能否处理没见过的表单格式"，**测不了"工程单据 schema 在真实手机拍摄照片上的表现"**。

→ 必须补 **20–50 张真实工程单据照片**做定性评估（哪怕只报失败模式分类），否则结论悬空——你的 F1 只证明了"能拟合自己造的数据"。

### 风险 3：Windows 环境

- Unsloth 官方对 Windows 的表述是 "works but expect package friction"
- Windows 上 FA2 = False（走 xformers / eager），训练慢于 Linux
- **第 1 周验收标准 = 跑通一次 2B 的 LoRA 训练。跑不通立刻切 WSL2，别恋战。**

### 风险 4：显存

见第四章。核心对策：2B + 384px + 短序列 + Unsloth。
