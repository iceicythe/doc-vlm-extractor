# 数据 Schema 设计 v1（草案）

> 状态：**已定稿** · 所有渲染、标注、评测均以此为准
> 关联：数据管线见 [`../src/build_dataset.py`](../src/build_dataset.py)，评测设计见 [`retrospective.md`](retrospective.md) 第 4 节

---

## 1. 设计原则

| 原则 | 说明 |
|---|---|
| **贴近真实** | 字段围绕建筑/工程造价单据的真实形态，不做玩具结构 |
| **可评估** | 字段名固定，便于计算字段级 F1；不接受模型自由发挥键名 |
| **可分层** | 分「核心字段」与「扩展字段」，MVP 只做核心，扩展按实验结论加 |
| **可迁移** | 与公开数据集（XFUND / WildReceipt）存在共同字段子集，支持跨域实验 |
| **保留原文** | 所有值以**字符串**形式输出，不做数字/日期类型转换（避免精度与格式争议，类型化留给后处理） |

## 2. 主 Schema：工程材料清单

### 2.1 完整结构（v1 目标形态）

```json
{
  "单据类型": "材料清单",
  "表头": {
    "项目名称": "西安某住宅楼主体工程",
    "供应商": "陕西XX建材有限公司",
    "单据编号": "CL-20260915-001",
    "日期": "2026-09-15"
  },
  "明细": [
    {
      "序号": "1",
      "名称": "螺纹钢 HRB400",
      "规格型号": "Φ12",
      "单位": "吨",
      "数量": "12.5",
      "单价": "4200.00",
      "金额": "52500.00"
    }
  ],
  "合计": {
    "金额": "107600.00"
  }
}
```

### 2.2 字段定义

**层级 0**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `单据类型` | string | 是 | v1 固定为 `"材料清单"`（预留扩展） |
| `表头` | object | 是 | 单据抬头信息 |
| `明细` | array | 是 | 物料行，**不定长**（1–8 行） |
| `合计` | object | 是 | 汇总信息 |

**层级 1：表头**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `项目名称` | string | 是 | 工程/项目名 |
| `供应商` | string | 是 | 供货单位 |
| `单据编号` | string | 是 | 形如 `CL-YYYYMMDD-NNN` |
| `日期` | string | 是 | **统一 `YYYY-MM-DD`** |

**层级 1：明细（每行）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `序号` | string | 是 | 行号，从 "1" 起 |
| `名称` | string | 是 | 材料名，中文 |
| `规格型号` | string | 否 | 如 `Φ12`、`C30`、`HRB400` |
| `单位` | string | 是 | `吨 / m3 / m2 / 个 / 套 / 米` |
| `数量` | string | 是 | 数字串，可含小数 |
| `单价` | string | 是 | 元，两位小数 |
| `金额` | string | 是 | 元，两位小数 |

**层级 1：合计**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `金额` | string | 是 | 所有明细金额之和 |

### 2.3 字段分层（应对训练难度）

| 层级 | 字段 | 定位 |
|---|---|---|
| **核心（MVP 必做）** | `序号` `名称` `单位` `数量` `单价` `金额` `合计.金额` | 表格提取的主干，也是那张测试图里已经出现的表头 |
| **扩展（实验后加）** | `表头.*`（4 个）、`规格型号`、`单据类型` | 增加任务完整度与真实感，但显著提高难度 |

> **理由**：那张零样本测试图证明模型连"序号/名称/单位/数量/单价/金额"六列都对不齐（把"名称"读成"材料"、丢了"数量"）。**先把这一层做扎实，比一开始就加表头更能拿到可信的对比数字。**

## 3. 公开数据集的映射

三个数据集**各自用各自的 schema 算指标，不跨集平均**（见 v2 第六章）。但要设计一个**共同字段子集**以支持跨域实验。

### 3.1 各自映射

| 数据集 | 原结构 | 映射为 |
|---|---|---|
| **XFUND-zh** | `question` + `answer` 经 `linking` 配对 | 扁平 `{字段名: 值}`，如 `{"受理时间": "2021年3月"}` |
| **WildReceipt** | 25 类逐文本框标注（key/value 分开） | 扁平 `{store_name, store_addr, tel, date, time, prod_item[], prod_quantity[], prod_price[], subtotal, tax, tips, total}` |
| **合成工程单据** | 渲染时直接构造 | 第 2 节的主 schema |

### 3.2 共同字段子集（跨域实验用）★

三个数据集都天然包含这三类语义：

| 共同语义 | 工程单据 | WildReceipt | XFUND-zh |
|---|---|---|---|
| **主体名** | 供应商 | `Store_name` | 各类机构/单位名 |
| **日期** | 日期 | `Date` | 受理时间/日期 |
| **总额** | 合计.金额 | `Total` | 各类金额字段 |

> **这支持一个非常有说服力的实验**：在 WildReceipt（英文收据）上训练"主体名/日期/总额"的提取能力，迁移到中文工程单据上看是否有效。
> 这就是 JD 里"**知识迁移**"的实证 —— 而且成本极低（复用已有数据，只改评测口径）。
> **建议纳入，但要放在核心实验之后**，作为加分项。

## 4. 评估口径

### 4.1 指标

| 指标 | 定义 |
|---|---|
| **字段级 F1** | 分数据集各自算；表头/合计字段按归一化后字符串严格匹配；明细按行对齐后逐字段算 |
| JSON 合法率 | 输出可被 `json.loads` 解析的比例 |
| 幻觉率 | 输出了 schema 外字段 / 图中不存在值的比例 |
| 单张成本 | 元/张（含能耗折算） |

### 4.2 明细行对齐规则（关键技术点）

明细是不定长数组，行对齐方式直接决定 F1 的含义。**规则（优先级从高到低）**：

1. **按 `序号` 字段对齐**（首选，符合直觉）
2. 序号缺失/重复时，按**行内容相似度**做贪心匹配
3. 仍无法匹配的行，计入漏抽/多抽

> ⚠️ 这个规则必须在评测脚本里**明确实现并记录**，否则 F1 数字会被质疑。面试也大概率会问"不定长表格你怎么评估"。

### 4.3 文本归一化（比对前）

```
去首尾空白 → 全角转半角 → 去除千分位逗号 → 
金额/数量统一小数位 → 日期统一 YYYY-MM-DD
```

**必须固定这套规则并写进文档**，否则同一份输出换个写法分数就变了。

## 5. 设计决策记录

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 扁平 vs 嵌套 | **嵌套** | 贴近真实单据；天然覆盖表格提取；区分度更高 | 扁平键值对（照抄公开集，太简单） |
| 值类型 | **全部字符串** | 避免精度/格式争议；类型化交给后处理 | 数字/日期类型（"12.50"→12.5 会引入无意义的错误） |
| 字段名语言 | **中文** | 面向中文工程场景；与 XFUND-zh 一致 | 英文（与业务场景不符） |
| 单据类型 | **v1 固定单一** | 先用一种跑通，降低难度 | 多类型混合（后续扩展项） |
| 明细行数 | **1–8 行不定长** | 真实且有区分度 | 固定行数（太假） |

## 6. 待你确认的问题

1. **字段分层是否同意？** 即 MVP 只做「序号/名称/单位/数量/单价/金额 + 合计」，表头 4 个字段和规格型号延后。
2. **是否需要"单价×数量=金额"的校验关系？** 真实单据满足这个等式。**满足 → 模型可利用此约束自查**（也是个很好的"可验证 reward"素材）；但不满足时会引入矛盾样本。我倾向**让 80% 的样本满足、20% 故意不满足**（模拟真实中的计算误差），并在 GT 里保留真实值 —— 这样能给模型一个"不能盲算"的信号。
3. **单位是否限定枚举？** 我建议限定为 `吨/m3/m2/个/套/米/千克` 七种，增加一致性、降低难度。
4. **日期格式是否统一 `YYYY-MM-DD`？** 真实单据里有 `2026年9月15日`、`2026/09/15` 等多种。**建议 GT 统一、渲染时随机** —— 这样模型学到的是"归一化能力"而不是"抄格式"。
5. **要不要现在就定"共同字段子集"实验？** 它很有说服力但会增加评测脚本复杂度。
