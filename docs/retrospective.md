## 0 一页速览

### 0.1 项目是什么

在**单张 8GB 消费级显卡**上，对 Qwen3-VL-2B 做 QLoRA 微调，解决**工程材料清单**（序号/名称/规格型号/单位/数量/单价/金额 + 表头 + 合计）的图片结构化提取，
并沿「数据管线 → SFT → DPO → 知识注入 → 自动化 prompt 优化 → Demo」做完整链路验证与多档对比。

选这个 schema 不是随意的 —— 广联达是建筑工程软件公司（BIM / 造价 / 施工），
材料清单正是其业务里天天出现的东西。

### 0.3 工程规模

- `src/*.py` 21 个脚本、约 7100 行
- 合成数据 **1000 模板 × 3 档退化 = 3000 张**（train 700 源 / val 150 / test 150 / test_ablation 83）
- 真实数据 4 个公开集全部解析（XFUND-zh 199 / WildReceipt 1767 / CORD / FUNSD）
- CPU 单测合计 **116 项**（API 39 / 参数回归 13 / Demo 自检 29 / DPO 数学 35）
- API 累计花费 **≈¥1.5**

### 0.4 一句话总结这 6 天踩坑的规律

> **这个项目里最贵的 bug，全部是「不报错的 bug」。**

空响应被当有效结果 → F1 悄悄掉 9pt；`load_dotenv()` 定义了没接线 → key 填了没用；
余额耗尽被降级成「优化无效」→ 退出码 0、Δ=0；adapter 切换失效 → 界面安静显示四份相同结果。
它们共同的特征是：**失败被伪装成一个看起来正常的结果**。
后半段的工程重点，基本就是把这类「静默失败」逐个焊死。

## 1 起点：方案评审与范围收敛（09-14）

### 1.1 做的事

评审最初的《多模态实习项目方案.md》，逐条核实外部事实（Unsloth 对 Qwen3-VL 的支持、
显存规格、Windows 限制、公开同构先例），给出 **9 条缺点**并重写为 v2。

### 1.2 挖出来的问题

**一级（会导致做不完）**

1. 工作量 ~150h vs 可用 150–200h，**零余量**；方案写 6 周却没解释剩下 4 周。
2. 「合成数据占 50% 工作量」是一句话压缩了一个独立工程（schema 设计 / HTML 模板 / 渲染 /
   退化 / 中文字体 / 印章 / GT 生成与对齐 / API 蒸馏 / 人工抽检）。

**二级（会让结果难看）**

3. **显存混淆了推理与训练** —— 方案里「4B 约 6GB」是 4bit **推理**数字。核实：4B BF16 推理
   min 9GB、8B QLoRA（16K 序列）实测峰值 20.2GB ⇒ 8GB 上 **2B 才是舒服区**。
4. 跨数据集平均字段 F1 **无效**（CORD/WildReceipt/自建 schema 无交集）⇒ 必须分集报告。
5. 合成到真实的 gap 无闭环（公开先例自己都承认没测）。
6. 无 Plan B —— PaddleOCR+规则在强格式字段上**可能反超 VLM**。

**三级（面试会被问穿）**

7. DPO ≠ 强化学习（是 RLHF 的免奖励模型闭式近似），叙事洞要提前补。
8. **JD 第 1 条的三个词只接了两个**，知识注入完全空白。
9. 四个模块**并列而非递进**。

### 1.3 关键决策

| 决策 | 结果 |
|---|---|
| 模型 | 锁 **Qwen3-VL-2B-Instruct**（Instruct 而非 Thinking —— 思维链对「直接输出 JSON」是纯负担） |
| 范围 | 收敛为 主项目 + DPO + DSPy ≈ 110–120h；**Agent 先不做** |
| 知识注入 | 一度被划走，**09-18 因拿到 JD 原文又加回来**（JD 第 1 条明写这个词） |
| 核心资产判断 | **不是模型，是数据管线** —— JD 里「知识注入」的真实含义就是「没有标注数据时怎么造出可用训练集」 |

> **教训（贯穿全程）**：项目薄 ≠ 功能少，而是**没有「发现」**。
> 加深的正确路径是 **不加功能，只加对照与分析**。这一条后来被反复验证：
> 消融、知识注入三点曲线、DSPy 三组归因，全都是「不加功能只加对照」的产物，
> 而它们产出的结论比功能本身值钱。

### 1.4 环境勘察（撞到的第一个硬门槛）

```
GPU        NVIDIA GeForce RTX 4060 Laptop GPU / 8188 MiB / compute cap 8.9 (Ada, bf16 OK)
驱动       537.53  ← 严重偏旧（约 2023 年底），仅支持 CUDA 12.2
transformers 5.17.0  ← 原生含 qwen3_vl 目录，最大门槛（>=4.57）已排除
缺失        unsloth / trl / peft / bitsandbytes / datasets / dspy 全无
```

**冲突**：Unsloth 官方 Windows 实测组合是 torch 2.10.0+**cu130**，而 537.53 只支持到 CUDA 12.2

- Windows 上 **FA2 = False**，`torch.compile` 对 Qwen3-VL 视觉算子报 InductorError，自动降级 eager。

## 2 阶段一：环境搭建（09-15 上午）—— 踩坑最密集的一天

### 2.1 坑 1：沙箱的「删除拦截」让 pip 装不完

**症状**：通过智能体执行环境跑 `pip install unsloth`，反复失败于：

```
[safe-delete][SAFE_DELETE_FAIL_CLOSED]
reason: windows-sandbox-recycle-bin-unavailable
ERROR: Could not install packages due to an OSError
```

**排查得到的关键特征**：
1. `dangerouslyDisableSandbox: true` **也无效** ⇒ 拦截不在 bash 沙箱层，在更底层的宿主文件保护层
   （删除操作被导向回收站，回收站不可用 → fail-closed）。
2. shell 的 `rm -rf` 正常（直接 unlink），**只有 pip 的删除路径被拦**。
3. 拦截目标随进度变化：`isympy.1 → fsspec → idna.exe → charset_normalizer/cli/__main__.py …`
   **修一个冒一个**。
4. 最阴的一点：**pip 先卸载旧包、后装新包**，中途被拦会留下「包被卸了、新的没装上」的**半坏状态**，
   产生无 RECORD 的包和 `~xxx` 残骸目录。

**处置**：agent 侧确实做不到 ⇒ **交给用户在本机原生终端跑**（无该层拦截）。
这是「长任务/敏感操作必须在用户终端」这条铁律最早的一次成型。

### 2.2 坑 2（**我自己犯的**）：pip 把 CUDA torch 换成了 CPU torch

**症状**：用户装完后 `check_env.py` 显示

```
torch         2.12.1+cpu        ← 从 2.5.1+cu121 变成 CPU 版
CUDA available: False
unsloth: [FAIL] NotImplementedError   ← 因 torch 无 CUDA
```

**根因**：**PyPI 上 Windows 版 torch 默认是 CPU 版本。** `pip install unsloth` 时 pip 从 PyPI
解析并从装成 `+cpu`。我这轮把命令简化成 `pip install unsloth dspy` 时忘了这一点 ——
更早的回复里其实给过正确顺序（先装 cu130 torch 再装 unsloth），**是我自己把它简化掉了**。

**处置**：

```powershell
.\venv-gld\Scripts\python.exe -m pip install --force-reinstall torch torchvision `
    --index-url https://download.pytorch.org/whl/cu130
```

必须加 `--force-reinstall`：`2.12.1+cpu` 与 `2.12.1+cu130` 的 public 版本号相同，
pip 会认为需求已满足而不重装。

**教训（已写进 README 顶部警告）**：**任何可能触发 torch 升级的 pip 操作，都必须带 `--index-url`
指向官方 CUDA 源。** 且修好之后**不要再跑 `pip install unsloth`**，否则又会被换回 CPU 版。

### 2.3 冒烟测试与一次「差点误读」的 loss

首轮冒烟：推理成功但**训练步抛 UnicodeDecodeError**。判断依据是「模型加载 ✅、推理 ✅」，
问题在测试代码本身（原脚本 `except` 只打印摘要、没打 traceback，所以看不到真因）。

修复三件事后重跑通过：
1. 加 `os.environ.setdefault("TORCHDYNAMO_DISABLE", "1")` —— 消除 InductorError 刷屏（疑与
   dynamo/inductor 缓存读写导致的 UnicodeDecodeError 相关）
2. 训练步改用标准对话模板（user + assistant 成对），替代原来 `prompt + target` 的粗糙拼接
3. `except Exception` + `traceback.print_exc()`

**结果**：

```
[推理 OK]  耗时 8.9s          ← 比首轮 26.6s 快 3 倍
[训练步 OK] loss=29.2270  耗时 0.6s
峰值显存 3.35GB / 余量 4.64GB
```

**关键判断：loss=29.2270 偏高是正常的，不是问题。**
因为冒烟测试里 `labels = input_ids.clone()`，对**整个序列**（含图像占位符 token 和 prompt）
都算了 loss，图像 token 的预测 loss 天然极高。
⇒ **正式训练必须用 Unsloth 的 `train_on_responses_only`**，只对 assistant 回复段计 loss。
（这一条后来在正式训练里落实，日志确认
`Enabled response-only masking on your UnslothVisionDataCollector`。）

### 2.6 这个阶段修掉的 7 个真 bug

| # | bug | 症状 / 后果 | 修法 |
|---|---|---|---|
| 1 | 供应商词表 typo `long昌` | 数据里出现错字 | 改 `隆昌` |
| 2 | **等式错误率口径**：原按「行级 20%」 | 多行样本几乎必然出错（实测 5 样本出 60%） | 改**样本级：85% 全对 / 15% 随机一行带误差** |
| 3 | 画布固定高度 | 1 行样本大片空白 | 高度自适应 |
| 4 | `shadow()` 广播维度错 `(H,W,3) *= (93,1)` | 报错 | 按行/列切片写入 `arr[:n] *= ramp[:,None,None]` |
| 5 | `motion_blur()` 用 7×7 核 | **PIL `ImageFilter.Kernel` 只支持 3×3 / 5×5** | 改 5×5 |
| 6 | `motion_blur()` 核未归一化 | 整体变暗 | 归一化 + 零核保护 |
| 7 | GT 文件名未区分 level | **heavy 覆盖了 medium 的 GT** | 改 `gt_degraded_{level}.jsonl` |

> 第 2 条的教训很典型：**「比例型参数」的单位是「行」还是「样本」必须写死在文档里。**
> 差一个量级，生成出来的数据分布完全不同。

### 2.7 首轮评测 0.98 之后，我自己泼的三盆冷水

12 条 test、挂 60 步 smoke LoRA：**F1 0.9802、JSON 合法率 100%、幻觉率 0%**，
零样本的四个失败模式（字段名误判 / 整字段丢失 / ```json 包裹 / 格式不受控）全部修复，
**嵌套 JSON 结构可学**这一最大风险解除。

但我同时标了三条局限 —— 事后看，这三条比 0.98 本身重要：

1. **同分布测试**：test 与 train 是同模板同词表，模型见过相同结构，**不可外推**。
2. **词表太小导致「猜词」**：供应商名错误**全部是词表内替换**（华建→中建、九州→大唐、
   宏远→远洋）⇒ 模型实际在学「从固定词表里选词」，这是合成数据的典型陷阱。
3. 未测外部数据。

**处置（词表扩充）**：

```
供应商名 = 地区(20) + 字号(200) + 业务后缀(8) = 32,000 种组合   （原 96 种，涨 333 倍）
项目名   = 地区(20) + 工程类型(12)            =    240 种组合   （原 72 种）
```

重生数据 → 1000 源模板 × 3 档 = 3000 张 → train 2100 / val 450 / test 450。

### 2.8 两个操作经验（后来反复用到）

1. **Bash / 命令的执行时限约 120 秒** —— `sleep 150` 会被掐断并返回空输出，
   容易误以为脚本挂了。等待请用 `sleep ≤ 100`。
2. **Python 输出重定向到文件时会缓冲**，中间进度看不到 ⇒ 脚本加 `-u` 或 `print(..., flush=True)`。

## 3 阶段二：跨域实验 —— 第一个「真实数据」证据（09-15 晚）

### 3.1 先修正一个概念错误（用户纠正）

我先前说「缺真实数据」，用户直接纠正：**「数据集上不有真实的吗」**。
准确说法是：已下载的四个数据集**全部是真实数据**（WildReceipt 真实拍摄收据 / CORD 真实小票 /
FUNSD、XFUND 真实扫描表单），**问题是领域与工程单据不匹配**，不是「没有真实数据」。
⇒ 概念一改，实验设计也跟着变：这些数据不是「凑数用的」，而是**测跨域泛化和灾难性遗忘**的。

### 3.2 XFUND-zh 的定位修正（重要）

解析 `linking` 字段还原 question↔answer 后，发现**内容与预期不符**：

```
高频字段：出生日期(42) 政治面貌(41) 姓名(39) 出生年月(34) 身份证号(29) 籍贯(28) 年龄(27)
⇒ 是「个人登记表单」（基金账户开户表），不是工程单据
```

| 原设想的用途 | 修正后的可行性 |
|---|---|
| 评测工程单据提取能力 | ❌ 字段体系完全不同 |
| **测「微调是否训坏通用能力」** | ✅ 这才是它的价值 |

已知质量缺陷：解析出的「键」混入噪声（`特别提示`、`▽业务类型` 等表单正文说明被误标为 question），
需要过滤规则（键名过长 / 含 `□☑▽√` 符号 / 含标点 → 丢弃）。

> **教训：数据集的名字和它的实际内容可能完全不是一回事。**
> 解析完必须先看「高频字段是什么」，再决定拿它干什么。

### 3.3 WildReceipt 解析与字段对齐设计

```
train 1204 条 / test 472 条 / 共 1676 条真实收据；每图字段数 1–9，平均 6.1
字段覆盖率：total 91% / date 84% / time 81% / store_name 78% / subtotal 71% /
           store_addr 69% / tax 68% / tel 59% / tips 5%
```

**设计决策**：只提取**单据级单值字段**，不做商品行配对（需按位置配对 name/qty/price，
复杂且评测口径模糊）。三个高覆盖字段与工程单据语义对齐：
`store_name ↔ 供应商` / `date ↔ 日期` / `total ↔ 合计` ⇒ 足以支撑跨域实验。

### 3.4 ⚠️ 一个 15 条样本得出的**错误结论**（必须记住）

**15 条时的结果**：

| 指标 | 零样本 | 微调后 | 变化 |
|---|---:|---:|---|
| F1 | 0.1587 | 0.1538 | 基本持平 |
| **召回率** | **0.1176** | **0.1176** | **完全一致（10/85）** |
| 幻觉率 | 26.7% | 46.7% | ↑ 近一倍 |

我当时的结论：**「微调没有损害模型的提取能力，只是改变了幻觉倾向」** ——
依据是「召回率 两次完全相同」。

**扩到 100 条后**：

| 指标 | 零样本 | 微调后 | 变化 |
|---|---:|---:|---|
| F1 | 0.3190 | 0.2842 | ↓ 10.9% |
| 精确率 | 0.5193 | 0.4467 | ↓ 14.0% |
| **召回率** | **0.2302** | **0.2084** | **↓ 9.5%** |
| 幻觉率 | 16.0% | 28.0% | ↑ 75.0% |

⇒ **召回率确实下降了 9.5%，先前的「完全相同」是噪声。**
准确结论应为：**轻度灾难性遗忘（可测）+ 幻觉倾向显著加剧**，两者叠加使 F1 降 10.9%。

> **教训（后来写进了所有对照实验的规范）**：
> **样本量 < 50 时，小数点后的差异没有意义。**
> 从 15 条扩到 100 条，同一个实验的 F1 从 0.1538 变成 0.2842（近翻倍）。
> 此后**所有对照实验的样本量下限设为 100**（后来因为评测时间成本，
> 消融子集定在 102 —— 刚好越过这条线）。

### 3.5 推理速度优化：31 s/条 → 9.9 s/条（3.1×）

**诊断过程（两步定位）**：

先测不同分辨率的输入序列长度：
```
384px → 156 token
512px → 268 token    ← Unsloth 实际使用（我设 384 没生效）
768px → 588 token
```
**输入很小 ⇒ 瓶颈不在图片**。

再测单条生成：
```
输出 184 token → 10.8s  (59 ms/token)
输出 563 token → 26.0s  (46 ms/token)
```
**⇒ 瓶颈是自回归生成，且输出长度差异极大（184 vs 563）**。

**处置**：`evaluate.py` 加 `--batch`（默认 4），批推理。

| | 单条 | batch=4 |
|---|---:|---:|
| 速度 | 31.0 s/条 | **9.9 s/条（3.1×）** |
| F1 | 0.9816 | **0.9833（无损）** |
| JSON 合法率 / 幻觉率 | 100% / 0% | 100% / 0% |

450 条完整测试集：4 小时 → **74 分钟**。

**一个后来越用越顺手的规律**：**耗时几乎完全由输出长度决定，与图片尺寸关系不大**
（工程单据输出 300–560 token → 9.9 s/条；英文收据输出约 30 token → 0.89 s/条）。

### 3.6 一个未解决但已解释的现象

Unsloth 日志提示 `Model does not have a default image size - using 512`：
我在预处理里 resize 到 384，但 **Unsloth 内部按 512 处理**。
视觉 token 更多 → 更慢，且与实验记录里的「384px」名义值不符。

这件事没有当场解决（需设 `processor.image_processor` 的 min/max_pixels 或用 Qwen3-VL 的
32 像素网格参数），但**后面对照实验严格要求「训练和评测用同一个 image-size」**，
所以横向可比性没有被破坏 —— 只是名义值与实际值有偏差，写报告时要留意。

### 3.7 图表：零依赖 SVG

matplotlib 未安装（装它又要用户跑命令）⇒ 改为**纯 Python 拼接 SVG**：
零依赖、每张 3–4 KB、在 README / 博客里比 PNG 更清晰。

### 3.8 顺手挖出一个会被面试问穿的口径问题

**schema 模式与 flat 模式的「幻觉率」口径不同，不可直接比较。**

- schema 模式：`flatten()` 只遍历预定义字段 ⇒ 模型多编的 **schema 外字段检测不到**
  ⇒ 合成数据上「幻觉率 0%」**不代表没有幻觉**
- flat 模式：遍历所有 key ⇒ 能检出，得 28%

⇒ 已在 `analyze_errors.py` 补上显式 schema 外字段检测。
**对外写文档时两个数字必须标注口径**，否则被追问即穿帮。

## 4 阶段三：评测框架的工程加固（09-16）

### 4.1 起因：一次 240/450 的静默中断

**现象**：`eval_v1_full.log` 停在 240/450，未产出 json。
**速度曲线单调劣化**：11.5 → 12.1 → 18.2 → 20.8 → 22.1 s/条（约 2 倍）。

**排查结论（当时确证，后来部分修正）**：不是 OOM，**是进程被智能体的执行环境杀掉** ——
前台命令有时限、后台任务会被回收，都会把进程掐掉而不报错。

> 后来在 09-17 还发现了**另一个**导致速度翻倍的真因（热节流，见 §5.5）。
> 两个原因**同时存在**，当时的排查只抓到了前一个。
> 这也是为什么后来立了规矩：**做对照实验前先看 `nvidia-smi` 的热降频计数。**

**最大的损失不是中断本身，而是**：当时 `evaluate.py` **只在结束时写文件** ⇒ 240 条推理全废。

**⇒ 立下铁律：任何 >30 分钟的任务必须在用户自己的终端跑，无例外。**
**⇒ 配套铁律：长任务必须边跑边落盘。**

### 4.2 三项加固（此后所有评测脚本的标配）

1. **增量落盘**：每批推理完即写 `eval_{tag}_preds.partial.jsonl` 并 flush，断电最多丢一批。
2. **断点续跑**：启动时读 partial 跳过已完成条目；用 `_meta` 行校验
   （adapter / data / image_size / prompt 指纹），**配置变了自动忽略旧缓存**。
3. **OOM 自动降 batch**：撞显存就把 bsz 减半重试直到 1，不再整批失败。
4. 新增 `--no-resume`。

### 4.3 ⚠️ 坑：续跑指纹用 `hash(prompt)` —— 会导致「白跑 30 分钟」

**这是本阶段最值钱的一个坑，而且踩了两次。**

`hash()` 在 CPython 里默认对 `str` / `bytes` **随机化哈希种子**（`PYTHONHASHSEED`），
同一个 prompt 在两次进程里的 `hash()` **必然不同**。

**后果不是「续跑失效」这么轻** —— 当时代码里指纹不匹配的处置是：

```python
if stale:
    partial.unlink(missing_ok=True)     # ← 30 分钟的推理当场蒸发
```

而且是在**「检测到配置变了」这个看起来完全合理的分支里**把数据删掉的。

**正解（两条一起做）**：

```python
import hashlib
fingerprint = {..., "prompt_md5": hashlib.md5(prompt.encode("utf-8")).hexdigest()[:16]}
```

1. 指纹用 `md5` / `sha1` 这类**稳定摘要**；
2. **不匹配时改名保留，永远不 `unlink`**，并把具体哪个字段不一致打出来：

```python
stale_keys = [k for k, v in fingerprint.items() if r.get(k) != v]
bak = partial.parent / (partial.stem + ".bak.jsonl")
partial.replace(bak)
print(f"  [续跑] 缓存不可用（字段不一致 {stale_keys}），旧文件 → {bak.name}")
```

3. **向前兼容**：旧版 meta 里可能只有不稳定的 `prompt_hash`，遇到「新 key 缺失 + 旧 key 存在」
   就跳过校验并提示，别让历史缓存全废。

**把这条钉进测试，而不是写在注释里** —— 断言常量证明不了稳定性，要真的换种子跑子进程：

```python
probe = ("import hashlib,sys;p=sys.stdin.read();"
         "print(hashlib.md5(p.encode()).hexdigest()[:16],hash(p)&0xFFFFFFFF)")
out = [subprocess.run([sys.executable, "-c", probe], input=prompt, ...,
                      env={**os.environ, "PYTHONHASHSEED": s}).stdout.split()
       for s in ("1", "2")]
assert out[0][0] == out[1][0]      # md5 稳定
assert out[0][1] != out[1][1]      # 内置 hash 必变 —— 病根被钉住
```

**付费 API 上这个坑代价更高**：本地档判 stale 只是浪费一次推理时间，
API 档判 stale 就是**整批请求重新计费**。所以凡是有断点续跑的 API 评测脚本，
指纹稳定性属于上线前必检项。（后来 `evaluate_api.py` 在跑 ⑤ 档之前真的复查并修掉了同源问题。）

### 4.4 评测子集从 450 → 102 条

评测是整批实验的时间大头（每条 15–20 秒）。此前经验「样本量 <50 时数字不可信」，
**102 条足够**（三档各 34），同时把时间压到可接受。

**关键设计：所有实验必须在同一批 102 条上评测**（`data/processed/test_ablation.jsonl`，
seed=3407），否则数字不可横向比。

### 4.5 工具层：`scripts/_run.py`

**问题**：在这台机器上用 PowerShell 调 python **抓不到 stdout**（exit 0 但零输出）；
PowerShell 重定向默认写 **UTF-16**，读回来是 binary。

**处置**：写一个通用子进程运行器 `scripts/_run.py`，把 stdout/stderr 落到 utf-8 文件。
两个必须的细节：

```python
env={**os.environ, "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1"}
```

**别漏 `env=` 那一行**：子进程默认按 Windows ANSI 代码页（GBK）写 stdout，父进程按 utf-8 解码
→ 中文全是替换字符。症状很迷惑：**有的脚本正常、有的乱码**（取决于输出的中文恰好能不能对上），
很容易误判成脚本本身的问题。

**另一个反复踩的坑**：`_run.py` 的 outname 是**相对 `outputs/`** 的 ——
传 `outputs/x.txt` 会写成 `outputs/outputs/x.txt`（踩过，清理过）。

## 5 阶段四：消融实验（09-16 → 09-17）

### 5.1 实验矩阵与变量控制

| tag | 变量 | 训练参数 | 控制逻辑 |
|---|---|---|---|
| 基线 | 384px / 100% / 全层 | 600 步 | — |
| abl_r512 | 分辨率 512 | 600 步 | **固定步数（同计算预算）** |
| abl_r768 | 分辨率 768 | 600 步 | 同上；显存风险最高 |
| abl_d50 | 数据量 50% | 300 步 | **按比例缩步数**（保 ≈2.3 epoch，才是真数据效率曲线） |
| abl_d25 | 数据量 25% | 150 步 | 同上 |
| abl_lang | 冻结视觉层 | 600 步 | 验证「视觉层该不该训」 |

**这个「步数怎么定」的设计本身就是关键**：比分辨率时固定步数（同预算），
比数据量时按比例缩步数（同 epoch）—— 两种变量要用两种控制方式，混了就没有意义。

### 5.2 最终结果（6 档全跑完，同一 102 条子集）

| 配置 | clean | medium | heavy | 总体 F1 | 训练 |
|---|---:|---:|---:|---:|---:|
| 384px · 25% | 0.9850 | 0.9764 | 0.9417 | 0.9666 | 20.6 min |
| 384px · 50% | 0.9868 | 0.9784 | 0.9562 | 0.9731 | 57.1 min |
| **384px · 100%（基线）** | 0.9886 | 0.9843 | 0.9635 | 0.9782 | 58.7 min |
| 512px | 1.0000 | 0.9971 | 0.9789 | 0.9914 | 57.3 min |
| **768px** | 1.0000 | 1.0000 | 0.9870 | **0.9953** | 70.6 min |
| 384px · 仅语言层 | 0.9894 | 0.9872 | 0.9627 | 0.9790 | 50.5 min |

### 5.3 三条结论（可直接复述）

1. **分辨率主导，且增益全在 heavy 档**：384→512 +1.3pt、→768 +1.7pt，
   heavy 从 0.9635 → 0.9870（+1.5pt），clean 直接满分。
2. **数据量 25% 才显形**（−1.2pt）：0.9666 → 0.9731 → 0.9782 单调、增量递减
   （+0.65pt / +0.51pt）⇒ 350 源样本接近饱和。
3. **冻结视觉层几乎无代价**：0.9790 vs 0.9782，差 0.0008 ≈ 3 个字段，属噪声
   ⇒ **显存紧张时不训视觉塔是安全选择**（比基线还快 14%）。

> ⚠️ 表述纪律：**不能说「视觉层无用」**，只能说「在本任务 / 本数据量下未见显著收益」。
> 这条直呼最初关于「要不要 finetune_vision_layers」的争议 —— 现在有自己数据上的答案了。

### 5.4 错误结构：分辨率与数据量各消灭一类错误

| 配置 | 错误字段 | 近似误读 | 语义误读（显著） |
|---|---:|---:|---:|
| 384px · 25% | 113 | 96 | 17 |
| 384px · 50% | 91 | 84 | 7 |
| 384px · 100% | 74 | 69 | 5 |
| 512px | 29 | 29 | **0** |
| 768px | **16** | 16 | **0** |
| 仅语言层 | 71 | 64 | 7 |

**核心叙事**：**数据量消除语义误读（17→7→5）；分辨率把它清零并把字符误读砍半（74→29→16）。**
而**结构层错误（幻觉 / 漏抽 / 行列错位 / JSON 非法）六档全为 0**
⇒ **瓶颈纯粹是字符识别精度，不是版面理解。**

### 5.5 ⚠️ 坑：把热节流误判成代码的锅

**现象**：`abl_d50` 重跑时 **10.8 s/step**，而 d25 当天早些时候 6.2、r512 5.2、lang 4.7、
r768 6.8 s/step。（注意：这个异常最初和 §4.1 的「进程被杀」混在一起，
直到 d50 重跑仍然慢才被单独拎出来查。）

**第一反应（错的）**：怀疑是自己刚加的 `UNSLOTH_CE_LOSS_TARGET_GB=1` 拖慢了。

**证伪**：算分块数 —— `n_chunks = ceil(S * 0.002264 / target_gb / 4) * 4`，
qlen≈1400 时 `target_gb=1` 与默认探测**都得到 4 个 chunk**
（只有 target ≥ 3.17GB 才会退化成 1 块）⇒ **env 变量在计算路径上不该有区别。**

**实锤**：

```bash
nvidia-smi -q -d PERFORMANCE     # 见 Violation Counters
SW Thermal Slowdown 累计 41721 秒（≈11.6h）   ← 软件热节流
HW Thermal Slowdown           0
```

笔记本连续跑了一下午 ⇒ **机器的锅，不是代码的锅。**

> **教训（写给未来的自己）**：本机上跑 benchmarking 类对照实验，**必须先看 `nvidia-smi`
> 的热降频计数**，否则会把热节流误判成代码改动的锅。
> 推论：**跨天/跨时段比较训练耗时没有意义**，要比就比 `s/step`，且必须在冷机状态。

### 5.6 ⚠️ 坑：Unsloth fused cross entropy 的「假 OOM」

**症状**：训练正常跑了几步后抛

```
RuntimeError: Unsloth: No or negligible GPU memory available for fused cross entropy.
报错点固定：unsloth_zoo/fused_losses/cross_entropy_loss.py::_get_chunk_multiplier
```

但 `nvidia-smi` 显示显存远没到顶（3.3GB / 8GB）。

**真因**：该函数在**训练过程中**调 `torch.cuda.mem_get_info(0)` 取空闲显存，
用 `free * 0.5`（上限 4GB）当分块预算。**Windows / WDDM 允许显存换页**，
这个读数会偶发返回接近 0 → 撞上除零保护直接抛异常。**不是真的缺显存。**

**排除项**：数据无长尾样本（train.jsonl 行长 median 1987 / max 2766，分布均匀）；
GPU 空闲（82MiB）时启动也会崩 ⇒ 与并发进程无关。

**处置**：固定分块预算，绕开这次探测 —— 在脚本最顶部（import torch 之前）：

```python
os.environ.setdefault("UNSLOTH_CE_LOSS_TARGET_GB", "1")
```

**验证**：同配置（`--data-ratio 0.5`）跑 20 步冒烟，**EXIT=0，通过原来必崩的第 7 步**。

**一个容易被误导的旁证**：这个崩溃在固定 seed 下是**确定性**的
（`--data-ratio 0.5` + seed 3407 每次都在第 7 步崩，重复 3 次都一样）。
所以「换个人少的数据比例就没事」不能说明问题解决了，只是没走到那个样本。
**修复必要且充分的证据**：显式 `UNSLOTH_CE_LOSS_TARGET_GB=""` 复跑 20 步，
**仍在第 7 步崩**。

### 5.7 ⚠️ 坑：HF 联网校验把训练卡死 2.5 小时

**症状**：`abl_r768` 16:00:31 启动，16:05:49 后**无任何输出**（僵死 2.5 小时）。
进程仍在（1.26GB 内存 + 2.5GB 显存），但 **GPU 利用率 0%**。
卡在 `HEAD https://hf-mirror.com/.../audio_tokenizer_config.json` 反复超时重试。

**关键判断**：r512 / lang 都成功加载过 ⇒ 是**网络间歇性抖动**，不是必然失败。

**处置**：模型早已完整缓存，但每次启动仍要联网做 HEAD 检查 ⇒ **`HF_HUB_OFFLINE=1`**。
验证离线模式可用（`AutoProcessor` 17.6s / `AutoConfig` 0.0s / unsloth 导入 22.5s）。

> **这个坑的症状是「日志停在加载模型不动」，极容易被误判成死锁。**
> 此后所有训练/评测命令都先设 `HF_HUB_OFFLINE=1`。

### 5.8 本阶段其他被修掉的 bug

| bug | 症状 | 修法 |
|---|---|---|
| `run_ablation.collect_levels()` 日志路径不一致 | **分档 F1 永远为空** | 改为传 log_dir |

## 6 阶段五：DPO —— 一个负结果，但归因做到位（09-17 → 09-18）

**动机**：跨域实验显示「微调把幻觉率从 16% 抬到 28%」。
DPO 的唯一目标就是把这个 28% 压回去。

### 6.1 第一件事：TRL 的 DPOTrainer **根本跑不了** Qwen3-VL

查阅 `trl/trainer/dpo_trainer.py`，vision 相关传参只有三处：

```python
model_kwargs["pixel_values"]         = ...
model_kwargs["pixel_attention_mask"] = ...
model_kwargs["image_sizes"]          = ...
```

**全文件搜 `image_grid_thw` 零命中。** 而 `Qwen3VLModel.forward` 必须有它才能把图像特征
scatter 回视觉 token 位置，`get_rope_index` 也要它算 mRoPE。

**对照组（决定性证据）**：同一个包里的 GRPO（`grpo_trainer.py:722`）和 OnlineDPO
（`online_dpo_trainer.py:1233`）**都显式传了** `image_grid_thw`，**只有离线 DPO 漏了**。

⇒ **这不是配置问题，改参数改不出来。结论：自写 DPO 循环。**
（"不是想自己写，是 TRL 走不通" —— 这句话在面试里很重要，避免显得重复造轮子。）

> **可复用的排查手法**：遇到「框架说支持多模态但报奇怪的形状错」，
> 直接 `grep image_grid_thw <框架目录>` 看哪些 trainer 传了、哪些没传 —— 比读文档快得多。

### 6.2 参考模型：`disable_adapter()` 是个陷阱

- 标准 DPO 的 ref 是**策略的初始快照**（= SFT 模型）。
- `disable_adapter()` 拿到的是 **SFT 之前的 base** ⇒ `β·log(π_θ/π_ref)` 里会混进
  **整个 SFT 阶段的增益**，起点就不是 0。
- 再加载一份完整模型当 ref → 4bit 的 2B 约 1.5GB + 激活，**8GB 必炸**。

**正解**：同目录再挂一份 adapter。

```python
model.load_adapter(sft_dir, "ref", is_trainable=False)
model.set_adapter("ref", inference_mode=True)   # 参考前向
model.set_adapter("default")                     # 切回策略
```

adapter 只有几十 MB，显存代价 ≈ 0，且语义正确。

### 6.3 低显存 logprob：别碰 `outputs.logits`

`outputs.logits` 是 `(B, T, vocab)` 的 float32。T≈1100、vocab≈152k 时**单份就 1.3GB**。

**做法**：取 `hidden_states[-1]`，**只对 completion 位置**过 lm_head，
vocab 维再分块做 `log_softmax` ⇒ 峰值从 GB 级降到百 MB 级。

**位置对齐（最容易写错的地方）**：`hidden[j]` 预测的是 `token[j+1]`，
所以给 `token[n_prompt:]` 打分要用 `hidden[n_prompt-1 : T-1]`。

### 6.4 ⚠️ 坑：`IndexError` —— vision 元数据没跟着延长

**报错**：

```
IndexError: The shape of the mask [516] at index 0 does not match
            the shape of the indexed tensor [231] at index 0
  at modeling_qwen3_vl.py:1088  get_rope_index
     input_token_type = input_token_type[attention_mask[batch_idx].bool()]
```

**根因**：自写循环只把 **prompt** 送进 processor，再把 completion 手工拼到后面 ⇒
`input_ids` / `attention_mask` 变成 `(B, P+L)`，但 processor 产出的
**`mm_token_type_ids` 仍是 `(B, P)`**。而 `get_rope_index` 要求两者严格等长。

**修复**（completion 段全是纯文本 token，**补 0 即正确**，不要动 prompt 段的图像标记 1）：

```python
def extend_mm_token_type_ids(mm_ids, n_total):
    if mm_ids is None or mm_ids.shape[-1] == n_total:
        return mm_ids
    pad = torch.zeros(*mm_ids.shape[:-1], n_total - mm_ids.shape[-1],
                      dtype=mm_ids.dtype, device=mm_ids.device)
    return torch.cat([mm_ids, pad], dim=-1)
```

**注意区分**：`pixel_values` / `image_grid_thw` 反而**不要**延长 ——
它们按图像条数（batch 的 leading dim）复制即可，图像本身没有变。

**配套**：加形状守卫，长度不符时在**跑前向之前**抛 `ValueError`，
别让 GPU 前向抛难读的 IndexError（还白跑一次前向）。

### 6.5 免费自检：step 0 的 loss 必须 = ln2

ref 与 policy 同源时逐 token 完全一致 → margin = 0 → **loss = ln2 = 0.693147**。
跑一个 batch 就能验完 adapter 冻结、形状、显存三件事，几乎零成本。

`--check` 实测：

```
序列长度 prompt=231  completion=285  total=516
mm_token_type_ids 长度 516 vs 序列 516  [OK]
policy logp chosen/rejected = -0.25 / -6.75
ref    logp chosen/rejected = -0.25 / -6.75   ← 逐位相同
step0 loss = 0.6931   (期望 0.6931)
峰值显存 3.56 GB    用时 3.6s
```

### 6.6 ⚠️⚠️ 更深一层的坑：ln2 自检**证明不了「切换生效」**

**这是本阶段最漂亮的一次自问自答。**

ref adapter 是 policy 的**逐位副本**，初始 logp 天然相等 —— 所以
「ref logp == policy logp」这个现象，在 `set_adapter("ref")` **完全失效、
前向一直在用 default** 的情况下**同样成立**。

**失效后果极隐蔽**：loss 曲线看起来完全正常（还是从 ln2 开始下降），
但 DPO 实际是在跟一个**「跟着策略一起漂移」的参考模型**对齐，**整个实验作废**。

**决定性做法：扰动 ref 的权重，看结果跟不跟着变。**
PEFT 把每个 adapter 的 LoRA 权重放在以 adapter 名为 key 的 `ModuleDict` 里：

```python
targets = [p for _, m in model.named_modules()
           if isinstance(m, torch.nn.ModuleDict) and {"ref", "default"} <= set(m.keys())
           for p in m["ref"].parameters()]
saved = [(t, t.detach().clone()) for t in targets]
try:
    with torch.no_grad():
        for t, _ in saved:
            t.mul_(1.5)
    ...跑一次切到 ref 的前向...
    # 结果变了 → 切换生效
finally:
    with torch.no_grad():
        for t, orig in saved:
            t.copy_(orig)        # 精确还原，别用乘除往返
```

实测：`ref 切换验证：扰动 ref 权重后 logp -0.2472 → -13.8441  [OK] 前向确实走 ref 权重`。

**单测覆盖 5 项**，其中最有价值的是**对照组**：
故意做一个不 honor 切换的假模型 → 探针**必须看不出变化**。
（没有这个对照组，探针本身可能是永远返回「变了」的假阳性。）

### 6.7 「让训练脚本可单测」—— 本阶段最值钱的工程做法

**把不依赖 `unsloth` 的数学写成模块级纯函数，把 `import unsloth` 全部放进 `main()`。**
这样 CPU 上就能 import 并单测：位置对齐、padding 屏蔽、分块一致性、loss 解析解、梯度方向。

`scripts/_test_dpo_math.py` 最终 **35 项**，测到的包括：
- `seq_logprob_masked` 与朴素 shift+gather 实现**逐元素完全一致**（max|Δ|=0）
- chunk=1 vs 128 结果一致；padding 确实被屏蔽；comp_mask 长度不符会明确报错
- `dpo_loss` 与解析解 `log(1+e^{-βΔ})` 一致；梯度 ∂loss/∂logp = ∓β/2
- policy == ref 时 loss == ln2

**训练脚本里的 off-by-one 是最贵的 bug（要跑几十分钟才暴露），先花十分钟测掉。**

**顺带纠正一个直觉错误**：β=0.1 时 5 nat 的 logp 差只折成 0.5 的 margin，loss 停在 0.474。
所以「DPO 的 loss 一直在 0.69 附近」是**正常的**，不是没学到。
（第一版测试按 β=1 的直觉写期望值，**虚报了两个 FAIL**。）

### 6.9 断点续跑：用 sidecar journal，不要「扫输出文件」

**起因**：用户提出「今天跑不完了」。原计划 200 图 × 31.7s ≈ 1h50m。

**先修了一个真实风险**：`build_pref_data.py` 原来是 `open("w")` 一次性写 + 块缓冲无 flush，
**崩在第 150 张就全部丢失**。

**正确做法**：`--resume` 读 sidecar journal `<out>.done`，跳过**已处理过**的源样本。

> **为什么不用「扫 `<out>` 文件」** —— 被**丢弃**的样本（无差异 / 分差小）不产出任何输出行，
> 扫输出文件会让它们**每次重跑一遍**，白烧算子。**journal 记录的是「处理过的输入」，语义才对。**

配合：每张图 `fout.flush()` + journal 写一行 ⇒ 最多丢当前这一张。

### 6.14 三层根因（**没有调参，直接定位**）

**第 0 步：先确认权重真的动了**（排除「lr 太小 / 没训动」这类无效怀疑）。
比两个 adapter 的 safetensors（秒级）：

```python
num = sum(((b[k].float() - a[k].float()).norm() ** 2) for k in a)
den = sum((a[k].float().norm() ** 2) for k in a)
print("相对变化", (num / den) ** 0.5)
```

实测：584 个张量里 **176 个变化 >1%**，全局相对变化 0.393%
⇒ **排除「没训动」，权重确实动了。**

**根因 1：50.3% 的 chosen 自身带错。**

| 指标 | 值 |
|---|---|
| chosen 平均 F1 | 0.9656 |
| **chosen 完全正确的对** | **49.7%** |
| 在 chosen/rejected 取值不同的字段中，chosen 正确的占比 | **66.9%** |

⇒ 465 个差异字段里只有 66.9% 是「chosen 正确」⇒ **梯度约 1/3 方向是反的**，
且噪声集中在金额(52)/供应商(32)/数量(23)/单价(18) 等核心字段。

> ⚠️ **分差大 ≠ 信号好**：本次 143 对的分差（0.0571）比探针（0.0485）更大，
> 但两者 chosen 质量一样烂。**挑对要看绝对质量，不要用 `min-gap` 当质量指标。**

**根因 2：错误性质超出 DPO 的能力范围。**

DPO 只能**重分配生成概率**，不能**增加输入信息**。

| 手段 | 错误字段 | 变化 |
|---|---:|---:|
| 基线 384px | 74 | — |
| 512px（**加信息**） | 29 | −61% |
| 768px（**加信息**） | **16** | **−78%** |
| DPO（同 384px，**调分布**） | 77 | **0%** |

判别方法：把多个**同分辨率、不同训练配置**的模型在同一批字段上对齐，统计
「同一 (样本, 字段) 在几个配置里出错」和「错值是否相同」——
实测 108 个错误字段中 **38.9% 在 4 个独立模型上稳定复现**、60% 的多配置错误「错成同一个值」
⇒ 是「看错了」（感知层），不是「选错了」（决策层）。

**根因 3：偏好数据与目标域异分布。**
143/143 全是**同域合成 heavy 档**，而幻觉率的现场在**英文收据域**（不同语言、版面、字段集）。
用同域偏好数据修跨域行为，方法层面就不成立。

**⇒ 决定：不再投入 DPO 调参**（即使只用完全正确的 71 对，感知层性质不变、上限很低）。

### 7.3 修了 4 件事

1. **`flatten` 全程类型防御**：

```python
def _as_dict(v):  return v if isinstance(v, dict) else {}
def _as_rows(v):  return [r for r in v if isinstance(r, dict)] if isinstance(v, list) else []
```

   新增 `_salvage_total` 处理 `合计` 标量。

### 7.4 顺带挖到一个会「删掉 30 分钟成果」的隐患

原续跑指纹用 `hash(prompt)`（同 §4.3）—— **这次的处置是 `partial.unlink()`**，
在 `--score-only` 下更是**先删文件再 FATAL**。

⇒ 已按 §4.3 的方案修掉（md5 + 改名保留 + 向前兼容 + `--score-only` 不做指纹门禁，
**真正的一致性由「图片名覆盖检查」保证，缺一条就 FATAL**）。

### 7.5 新增 `--score-only`（评测分家的关键）

只读 partial + 重打分，**不 import torch/unsloth、不加载模型**，秒级完成。

实现要点：把 `import torch` / `from unsloth import ...` 放进 `if not args.score_only:`，
模型加载同样条件化。

> **这条工程约束值得单独强调**：推理和打分是两个**成本完全不对等**的阶段
> （数十分钟 GPU vs 数秒 CPU），所以**打分层任何 bug 都不能连累推理结果**。
> 打分层要能被反复重跑，且必须零成本。

**顺带修掉两个小问题**：
- 前一版 `import torch` 在 `main()` 顶层，`--score-only` 下需要条件化；
- f-string 里带条件表达式 + 转换符（`{x.get('k')!r if x else '?'}`）这种**嵌套引号**
  在 **Python < 3.12 直接 SyntaxError** —— venv 是 3.12.6 所以侥幸没炸，已改成 `%` 格式化。

## 8 阶段七：知识注入（09-18 晚）

### 8.1 先做可行性前置检查 —— 这一步推翻了最初的判断

**「错误率高」≠「可改进」。这是本项目最容易踩的认知陷阱**：
你会本能地去修错误率最高的字段，但那些字段往往恰恰是**修不了的**。

拿训练集 GT 建各字段值域（词表 = `train.jsonl` 2100 条的 GT），统计测试集命中率：

| 字段 | 词表不同值 | 测试集命中率 | 零样本错误率 | 结论 |
|---|---:|---:|---:|---|
| 供应商 | 692（随机） | **1.0%** | **87.76%** ← 最高 | ❌ 救不了 |
| 单据编号 | 698（随机） | **0.0%** | 79.59% | ❌ 救不了 |
| 项目名称 | 231 | 98.0% | 80.61% | ✅ 对症 |
| 日期 | 259 | 91.2% | 43.88% | ✅ 可用 |
| **名称** | **20** | **100%** | 21.94% | ✅✅ 收益最大 |
| **规格型号** | **37** | **100%** | 31.12% | ✅✅ |
| 单位 | 5 | 100% | 9.69% | 空间小 |

**三条关键洞察**：

1. **供应商 / 单据编号是逐条随机生成的**（2100 条 → 692 / 698 个不同值，几乎无重复）
   ⇒ 测试集的正确值**根本不在词表里** ⇒ 任何「词表纠正」都会**把对的改错**。
   **而这恰好是零样本错误率最高的两个字段。**
2. 反过来，`名称`(20 值) / `规格型号`(37 值) 是**真闭集**，命中率 100%
   ⇒ **把开放式生成变成 20 / 37 选 1，收益最大**。
3. **可量化上限**：闭集可纠正字段的错误数
   = 名称 90 + 规格型号 128 + 项目名称 79 + 日期 43 + 单位 38 = **378**，
   占全部 871 个错误字段的 **43.4%** ⇒ 值得做，且上限可预估。

**判据：词表命中率 × 错误数量 = 理论收益上限。**

**顺带一个数据集设计缺陷（写进报告了）**：供应商 / 编号用无重复随机值，
使这两个字段退化成「**纯 OCR 测试**」，**夸大了感知难度** ——
真实场景里供应商就那几家、编号有规律，先验是可用的。

### 8.2 三级规则 + 一个结构性保证

1. 归一化后**精确命中** → 采纳规范写法。
   ⚠️ **这一步不改变分数**（打分前本来就会归一化），只统一输出写法。
   **别把它算进「收益」**，否则会自我欺骗。
2. 否则模糊匹配：`top1 相似度 ≥ min_sim` **且** `与次优差 ≥ min_gap` → 替换
3. 否则**原样保留**

> **`broke`（改前对 → 改后错）恒为 0 是结构性保证，不是调参调出来的**：
> `模型输出对 ⇒ 该值 == GT ⇒ GT 在词表内 ⇒ 精确命中 ⇒ 走规则 1、不改`。
> **只要词表覆盖住了 GT，改坏在数学上不可能发生。**
> 实测佐证：1260 个可比实例里只有 2 个 GT 在词表外 —— gap=0.05 时 broke 恰为 0，
> 把 gap 放宽到 0 就恰好冒出 1~8 个，完全对得上。

### 8.3 结果

| 档位 | 可比实例 | 改动 | 仅统一写法 | fixed | broke | F1 前 | F1 后 | ΔF1 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| ② 2B 零样本 | 1260 | 183 | 70 | 169 | **0** | 0.7349 | **0.7870** | **+0.0522** |
| ③ 2B SFT 384px | 1335 | **1** | 203 | 0 | 1 | 0.9782 | 0.9779 | −0.0003 |

宽容口径：0.7471 → 0.7985（+0.0514）。

### 8.4 两个阈值都不是拍脑袋定的

**`min_gap` 不可省**：从 0.05 放宽到 0，sim=0.50 时改动 183 → 224（多改 41 处），
而 ΔF1 只从 +0.0522 到 +0.0525；**含日期时 `broke` 从 0 涨到 8**。
原因：同模板字段彼此极像（一批 `X市政道路改造工程`），**没有 gap 就无法判断该改成哪一个**。

**`min_sim` 取「边际有效率」的拐点，不取最高分**：

| 区间 | 新增改动 | 新增 fixed | 有效率 |
|---|---:|---:|---:|
| 0.70 → 0.60 | +17 | +13 | 76% |
| 0.60 → 0.50 | +37 | +34 | **92%** |
| 0.50 → 0.40 | +14 | +6 | **43%** ← 拐点 |

⇒ 默认 0.50。

**日期默认关闭**：开启 +0.0065（0.7870 → 0.7935，broke 仍 0），
但收益依赖「日期池有限」这一数据特性。**真实场景日期是连续值**，
`2026-06-26` 与 `2026-06-25` 相似度约 0.91，模糊匹配会混淆相邻日期。

### 8.5 ⭐ 最有价值的发现：收益与基座能力成反比

**183 处改动（零样本）→ 1 处（SFT）。**

SFT 之后词表纠正**无事可做**，因为 **SFT 已经把词表内化进权重**。
更妙的是「仅统一写法」反而从 70 涨到 203
（SFT 输出的值几乎全在词表里，只是空格 / 符号写法不同，归一化后等价）。

⇒ 这与项目主线「**SFT 买到的是读写中文字段**」**相互印证** ——
**词表归一化是同一件事的另一种（外部）实现，所以两者收益高度重叠。**
这条对照比 +0.0522 本身更有说服力。

**通用原则：做任何后处理类改进前，先确认基座确实没有这个能力，否则纯属白干。**
**反向看**：这条对照本身就是「微调买到了什么」的强证据。
**执行条件**：想拿到这条曲线，**至少要有两个能力差距明显的基座**
（一个弱、一个强、一个已被微调）。只有一个档位时，你无法判断收益是「方法有效」还是「基座太弱」。

### 8.6 「要不要加 RAG」的判断（用户随口问过一次）

**核实结果：完全没做**，且是方案文档里明确划走的（划给了「别的项目」）。

**关键判断：本项目的知识注入不需要 RAG。**
候选集规模 名称 20 + 规格型号 37 + 单位 5 + 日期 259 + 项目名称 231 ≈ **552 个值**，
全量塞进 prompt 也只是几百 token ⇒ **检索层是纯负收益**：
省不下 token，还凭空引入一条「召回失败」的新失败模式。

| 候选集规模 | 该用什么 | 检索层 |
|---|---|---|
| ≤ 10³ | **全量注入 或 后处理归一化** | 无收益 |
| 10³ – 10⁵ | 检索 top-k（RAG） | 有价值 |
| > 10⁵ | 分块 + 向量库 + rerank | 必需 |

**对外口径固定为**：「候选集 552 个值，走全量词表 + 相似度阈值的保守纠正」——
**不说「我做了 RAG」**。（真正需要 RAG 的是「企业物料主数据 / 全量定额库」量级。）

### 8.7 主动写出来的局限

阈值是在**测试集**（n=102）上扫的。诚实做法：默认值取自「边际有效率拐点」而非最高分，
并在报告里显式注明这条局限 —— 比装作没这回事更经得起追问。

**产出**：`report_inject_sweep.md`（阈值扫描 + 档位对照，独立保留）、
五个逐配置注入报告（② 零样本两档阈值、③ SFT、⑤ API 两档 —— 已合并进
`outputs/reports_appendix.md` §2）、`eval_{zero_abl,abl_base}_inj_preds.jsonl`
（结构同构，下游分析脚本可直接吃）。

## 9 阶段八：⑤ 商用 API 档（09-18 晚 → 09-19）

### 9.1 选型：为什么一度想用 Qwen3-VL-Plus，最后跑了 DeepSeek

**首选 Qwen3-VL-Plus（阿里云百炼）的决定性理由不是能力，而是「同源对照」**：

本地 SFT 的基座是 Qwen3-VL-2B，用**同家族** API 做上界，
五档里的 VLM 行就变成**一条单家族缩放曲线**（2B 零样本 → 2B SFT → 8B 零样本 → VL-Plus API），
prompt 格式 / tokenizer / 图像预处理完全一致，**增益只能归因于规模**，
排除了「换个家族所以 prompt 不匹配」这个 confounder。

**但百炼需要实名认证，key 一直没到位；DeepSeek 的 key 现成 ⇒ 先跑 DeepSeek。**

**这一步的代价必须说清**：现在表里的 ⑤ 是**跨家族上界**，不是同源上界，
**引用时别把归因说满**（只能表述为「跨厂商上界参考」）。

### 9.2 provider 核实的三个坑（官方文档实查）

1. **只有 `deepseek-flash` 支持图像**，`deepseek-v4-pro` 传图直接 400
   ⇒ **名字里带 "pro" 不等于能力更强，得实测。**
2. **每张图上限 1024 tokens**（第三方博客说 384，是旧信息，以官方为准）。
3. 官方 resize 规则：总像素 < 约 544×544 的**放大**；更大的**缩到等效 1300×1300**。

**实测自己数据的视觉 token（按 32px 合并 patch 粗算 `ceil(w/32) * ceil(h/32)`）**：

| 数据 | 抽样尺寸 | 视觉 token | vs 1024 上限 |
|---|---|---|---|
| `test_ablation`（合成单据） | 760×360 左右 | **288**（max 375） | ✅ **零损失** |
| `wildreceipt_test`（真实收据） | median 495×845，**max 3348×5952** | median 501，**max 19530** | ⚠️ **高瘦票据被压约 8 倍** |

⇒ **DeepSeek 跑同域是干净的**（等于拿到原生分辨率）；
**跑跨域时分辨率成为 confounder**，分数低分不清「模型不行」还是「图被压了」。
而跨域正是判定「瓶颈在模型能力」的关键档。

> **通用判据：选 provider 之前，先按自家数据算视觉 token，别信「支持图像」三个字。**
> 各家有每图 token 硬上限，而且裁剪规则不同。**同一批实验里，长边图片的风险完全可能在
> 另一批数据上不存在。**

### 9.3 `src/evaluate_api.py` 的设计取舍

**最重要的一个决定：打分代码只能有一份。**

用 `importlib` 按路径加载 `evaluate.py`，直接复用 `score_one` / `prf` / `flatten`，
**不另写一套**。已验证加载时不会把 torch/unsloth 拖进来（它们只在 `main()` 里 import）。

理由：两份实现必然慢慢漂移，而「哪一档更高」这种结论最怕口径不一致。

**配套**：产物与 `evaluate.py` **完全同构**的三件套
（`eval_{tag}.json` / `_cases.txt` / `_preds.jsonl`，字段一致）
⇒ `analyze_errors.py`、`check_amount_consistency.py`、`analyze_error_consistency.py`
**可直接吃**，能与本地各档并列进同一张表。

**其他设计**：
- `--provider {deepseek,qwen}`，两个端点都是 OpenAI 兼容协议
- key 从 `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 读，不落盘、不进 git
- **默认送原图**（`--image-size 0`）：本地上界是 768px，「上界对照」就该给足分辨率
- 断点续跑 + 并发 4 + 429/5xx 指数退避 + 单条失败即中止（不静默吞）
- `--check` 自检：发 1 张图，打印原始返回 + token 用量 + 预估花费，不写产物
- `--list-models`（调 `/v1/models`）：模型 ID 随区域/实现变，404 是这类脚本最可能的翻车点

**一个反直觉的实测发现**：合成图是干净线条，**1000×1000 原图 PNG 的 base64（51.8KB）
比缩放到 384 后的（68.9KB）更小** —— 缩放引入的抗锯齿渐变让 PNG 压不动了。
⇒ 所以「送原图」既更清晰、payload 也更小，两全。
（我最初的测试断言写反了，已修正为记录这个事实。）

**端到端校准**：单测里用假 client 回吐 GT，**F1 必须正好 1.0**。
打分口径若有任何偏差（字段拍平、归一化、行对齐），这一条立刻炸。

### 9.4 ⚠️ 静默 bug #1：`load_dotenv()` 定义了但没接线

**症状**：「明明把 key 填进 `.env`，仍报环境变量未设置」。

**根因**：函数写好了，`main()` 里**从未调用它**。典型的「写完忘了接线」。

**修法**：`main()` 顶部调用；`load_dotenv(path=None)` 加可选参数以便单测注入临时文件。
**加一条接线回归测试**：monkeypatch 掉 `load_dotenv`，断言 `main()` 调用过它。

### 9.5 ⚠️⚠️ 静默 bug #2：空响应被当成有效结果（F1 悄悄掉 9.2pt）

**原代码**：

```python
return resp.choices[0].message.content or ""
```

空响应 / 半截响应被静默当有效结果，**且从不检查 `finish_reason`**。

**实测后果**：102 条里 **16 条**中招（9 条空串 + 7 条断在 JSON 值中间，
长度 201~966 字符，**不是 token 上限截断**）
⇒ 落盘成 `json_valid=False` ⇒ 整条按「全没抽到」计分
⇒ **同域 F1 从 0.9546 悄悄掉到 0.8622，全程不报任何错。**

**修法两条**：

1. 空响应 / `finish_reason == "length"` → **退避重试**
2. **续跑缓存拒绝空响应** —— 否则瞬时故障会被「续跑」**永久固化**，
   重跑一百遍也补不回来（这次是靠手工清理缓存行才救回来的）

> **教训（写进面试口径也行）**：**这类 bug 不崩、不报错，只是安静地让指标变难看。**
> 当时若直接抄下 0.8622，结论会变成「商用 API 全面不如本地小模型」—— 完全站不住。
> **判据：指标突然变难看时，先查数据管道，再下模型结论。**
> 查管道的第一步：**看非法/失败样本的预测长度分布**，
> 一串 0 或半截长度就是管道故障，不是模型能力。

### 9.6 ⚠️ 必须显式传的参数：`--max-new-tokens 4096`

`--max-new-tokens` 默认 **768** 是跟着本地 8GB 显存定的（`evaluate.py` 同值），
**API 侧没有这个约束**。

实测一张 3–4 行明细的工程清单要 **1369 completion token** ⇒ 768 会直接把它截断成非法 JSON。

> **本地与 API 不要共用同一个 `max_tokens` 常量。**

### 9.7 ⚠️⚠️ 静默 bug #3：`--no-thinking` 对 DeepSeek 是**彻头彻尾的空操作**

**怎么发现的**：为 DSPy 方案探路时做了个 `dspy.Image` 探针，打印用量看到
`completion_tokens=2845`，其中 **`reasoning_tokens=2563`**
⇒ **说明 DeepSeek 默认就在思考模式上烧掉九成输出。**

回头查 `evaluate_api.py`：`--no-thinking` 的实现只有 `extra.pop("enable_thinking")`，
而 `enable_thinking` 是 **DashScope 的方言**；DeepSeek 的 `extra` 本来就是 `{}`,
**所以这个开关对 DeepSeek 完全没用 —— ⑤ 档一直是带着思考跑的。**

**两家端点的思考模式方言**：

| 端点 | 关闭写法 | 默认 |
|---|---|---|
| DashScope | `enable_thinking: false` | **已关** |
| DeepSeek | `thinking: {"type": "disabled"}` | **开着（不传 ≠ 关闭）** |

**实测 4 种写法**：`thinking=False`（bool）直接 **422**；
`thinking={"type":"disabled"}` 与 `reasoning_effort="none"` 都有效。
已抽成纯函数 `build_extra(provider, thinking, no_thinking)`。

**修完重跑（同域 n=102，同一 `--max-new-tokens 4096`）**：

| 配置 | F1 | JSON 合法 | 耗时 | 花费 |
|---|---:|---:|---:|---:|
| ⑤ `thinking` 开（原数字） | 0.9546 | 100% | 慢 | ~¥1 |
| ⑤ **`thinking` 关** | **0.9681** | 100% | **35s** | **¥0.14** |

⇒ **思考模式在这个任务是负收益**：F1 反低 1.35pt，成本高约 7 倍。
合理 —— 任务是「感知 + 格式化」，不需要推理；**思考反而诱发对图片内容的过度解释**。

**单测 33 → 39 项**，新增 6 项钉住方言差异（deepseek 三种开关组合 + qwen 三种），
**防止再写成空操作**。

> **动手前先探一次 `reasoning_tokens` 是不是 0。** 这个数不用猜，
> `usage.completion_tokens_details.reasoning_tokens` 直接能看到。

## 10 阶段九：DSPy / GEPA 自动 prompt 优化（09-19）

### 10.1 先问「值不值得做」

| 档位 | 是否值得 | 理由 |
|---|---|---|
| ③ SFT | **否** | prompt 已被内化进权重（硬证据：SFT 档词表注入只改动 **1 处**），改推理 prompt 反而制造训练/推理不匹配 |
| ② 2B 零样本 | 可以 | 但需自建 `dspy.LM` 包装 Unsloth |
| **⑤ API** | **最优** | API 直连，且优化后可用 `evaluate.py --prompt` **回流本地验证** |

**优化器选 GEPA**（反射式，**只改 instruction 不塞带图 demo** ——
VLM 场景塞带图 demo 会让 token 爆炸）。

**技术探路（已实测，成本几厘钱）**：`dspy.Image(data_uri)` + `dspy.LM("openai/deepseek-flash", ...)`
**通路可用**（dspy 3.3.1 的多模态序列化走 litellm，`openai/` 前缀走 OpenAI 兼容路径）。

**顺手发现**：signature 的 docstring 不写 schema 时，**模型会自己发明结构**
（实测输出扁平 `{项目名称, 供应商, 日期, 编号, 材料清单, 合计金额}`，
而 GT 是嵌套 `{单据类型, 表头, 明细, 合计}`）
⇒ **这正是 DSPy 能优化的东西 —— instruction 质量直接决定结构合规率。**

### 10.2 口径设计（复用性最强的一条）

评测集 = `wildreceipt_test.jsonl` **前 100 条**（与 ⑤ 档相同）；
trainset 101–124 / valset 125–164 ⇒ **优化过程从未见过评测集**。

**两条硬口径**：

1. **dspy 内的分数只用于优化，正式数字必须由 `evaluate_api.py` 产出。**
   因为 dspy 发给模型的是 `instruction + 字段名 + 格式要求`，**不等于 instruction 原文**，
   与「把 instruction 当裸 prompt 发出去」不是同一个东西。**两边混谈会得出错结论。**
2. VLM 场景只改 instruction，不塞带图 demo。

### 10.3 four 个坑

**坑 1：`from __future__ import annotations` 会让 dspy 直接崩**

```
ValueError: Field types must be types, but received: ForwardRef('dspy.Image')
```

它把注解变成字符串，dspy 解析 Signature 时拿不到真实类型。
**含 `dspy.Signature` 的文件里绝不能加这一行。**

**坑 2：GEPA 的 `log_dir` 复用会静默加载旧状态**

见到已有 run dir 就续跑。若两次运行的 valset 规模不同（smoke 8 条 → 全量 40 条），
状态错位后在 `_evaluate_programs_on_valset` 抛 `IndexError` —— **报错点离真因隔了好几层。**
⇒ 用带时间戳的独立目录，每次都是干净状态。

**坑 3：litellm 启动去 GitHub 拉价格表，白等 41 秒**

国内网络必然超时重试 3 次。**必须在 `import litellm` 之前**设：

```python
os.environ.setdefault("LITELLM_LOCAL_MODEL_COST_MAP", "True")   # 41.0s → 2.7s
```

**坑 4（⭐ 最值钱）：余额耗尽被静默降级成「一个正常结果」**

**症状**：GEPA 跑完 200 轮预算、**退出码 0**、最后打印
`baseline 0.5205 / optimized 0.5205 (Δ +0.0000)`，看起来像「优化无效」。

**真相**：**开跑 3 分钟后余额就耗尽了，之后 396 次调用全部失败**，
一个有效候选都没产出，最后把 **baseline 原文当「最优指令」写盘**。

**这是同一族静默问题的第三次**：
① 空响应被当有效结果 → F1 悄悄掉 9.2pt
② `load_dotenv()` 定义了没接线
③ 余额耗尽 → 得出「优化无效」的**反向错误结论**

**两道闸（都值得抄）**：

1. **preflight**：开跑前发一次极便宜的请求确认端点可用。余额/鉴权错就**立刻退出（返回码 1）**，
   别浪费 20 分钟。判据用关键字匹配：`insufficient balance` / `insufficient_quota` /
   `invalid_api_key` / `unauthorized`（这类错误重试无意义）。
2. **结果自检**：若最优 instruction 与基线**一字不差** ⇒ 打印醒目警告 + **返回码 2**。
   明确区分「Δ=0 因为没跑成」和「Δ=0 因为优化无效」。

> **通用原则**：任何「优化器 / 搜索器」跑完后，都要问一句
> **「它的输出真的变了么？」** 没变就不是「无提升」，是「没跑成」。

### 10.5 ⭐⭐ 三组归因对照 —— **本项目方法学上最有价值的产出**

**只看「优化前 0.4408 → 优化后 0.6830」，结论会写成「DSPy 使跨域 F1 +24pt」——
听起来漂亮，但它是错的。**

补一组「人工机械补字段」（把字段清单从 3 个抄到 8 个，其余一字不动）：

| 组 | prompt | 留出 100 条 | valset 40 条 |
|---|---|---:|---:|
| A | 手写 3 字段 | 0.4408 | 0.5191 |
| **B** | **手写 8 字段**（人工机械补齐） | **0.7085** | **0.7734** |
| C | GEPA 优化版 | 0.6830 | 0.7447 |

⇒ **补字段 +26.8pt；GEPA 额外的措辞规则 −2.6pt。**
⇒ **C 连 B 都没打过** ⇒ **GEPA 的全部贡献是「诊断」（发现字段清单缺失），
而不是它写出来的那些规则。它的规则是负贡献。**

**为什么必须两个数据集都测**：只在留出集上看到 C<B，还能赖「噪声」；
C 是在那 40 条 valset 上按分数选出来的，而 **valset 上同样 C<B** ——
这才让「过拟合小验证集」**从猜测变成证据**。多花 ¥0.11，值。

**C 到底输在哪？按字段拆开看才看得出来**：

| 线索 | 值 |
|---|---|
| 损失形态 | **均匀小亏、无单点崩溃**（除 `tel` 外每字段 −0~3 tp） |
| 最大一块 | `tel`：**−7 tp / +10 fp**（电话号最容易在边角处被误读） |
| FP 总量 | 201 → **219** |
| 真因 | 它替换上来的**激进召回规则**：「必须逐项检查顶部/底部/页脚/边角」「只要图中出现，就应提取」 |

⇒ **同一条规则在「漏抽 4 个字段」时是解药，字段补齐之后就过量了。**
「往某个方向推」的规则没有绝对对错，取决于当前缺口有多大 ——
**这也是为什么基线已经很高时继续加规则，往往只买到 FP。**

### 10.6 ⭐ 第一铁律：写归因前，先确认「你评的是哪一版产物」

**差点栽在这里**：翻日志看到某个候选写着「值规范化去空格」「示例里加 `tips`」这类明显错规则，
就当成了「GEPA 写错的地方」写进报告。

**但那其实是第 1 轮的中间候选（val 0.6413）—— 第 2 轮它自己把这些全删了。**

导出的最终版（val 0.7490）里明写着
「字段值必须严格保留图片中的原始写法，**包括空格**」，字段清单里也没有 `tips`。

⇒ **归因要对着「导出的那个文件」逐条读，不要凭日志里某一轮的印象下判断。**
否则会出现「文档说它去空格、产物里却写着保留空格」这种一读就露馅的矛盾。
（**日志里保留逐轮 `Proposed new text`，是这里能翻案的关键 —— 别把日志删了。**）

### 10.7 ⭐ 第二铁律：别凭想象描述自己的打分口径

本例的 `evaluate.normalize()` **会去掉值里的所有空白和逗号**
（`"50-01 NORTHERN BOULEVARD"` 与 `"50-01NORTHERNBOULEVARD"` **等价**），
键名另做宽松匹配（忽略大小写 / 下划线 / 连字符）。

早前一版文档把这个**写反了**（说「打分层对值保留空格」）—— **被追问就会当场露馅**。

⇒ **写「打分层对 X 怎么处理」之前，去读那个函数，或至少跑一行**：

```python
import sys; sys.path.insert(0, "src"); import evaluate as ev
print(repr(ev.normalize("50-01 NORTHERN BOULEVARD")))
```

### 10.8 ⭐ 第三条产出：改写了「跨域不能用」的口径 —— 召回天花板

**一个只靠读数据就能发现、却极容易漏掉的坑。**

某数据集真值 100 条共 **643** 个字段（平均 6.43 / 样本），而评测 prompt **只点名 3 个**：

```
被点名的真值字段 / 真值字段总数 = 268 / 643 = 0.4168   ← 精确的 recall 上限
（粗估「3 / 6.43 ≈ 0.47」也能用，但写进报告要用实测的 0.4168）
```

⚠️ **别用「字段种类数 / 平均字段数」去算**（会把 `tips` 这种稀疏字段算重），
要用**逐条累加**的 `被点名字段数 / 字段总数`。

**这条天花板直接改写了原来的结论**：

- ⑤ 档原跨域 **F1 0.4408 / recall 0.3157** ⇒ 是天花板的 **75.7%，不是「贴着」**
  （**还有 24pt 空间** —— 这正是补字段能涨 +26.8pt 的原因）
- 补到 8 字段后：天花板 → **0.9907**，F1 **0.7085**、recall 0.7201

⇒ **「跨域掉到 0.44，说明模型不行」这个结论站不住：相当一部分是「评测 prompt 的口径缺陷」，
不是模型能力。**

**动手前 30 秒就能做的检查（纯 CPU，不用跑模型）**：

```python
import json, re
key = lambda s: re.sub(r"[\s_\-]+", "", str(s).lower())
ASKED = {"store_name", "date", "total"}
rows = [json.loads(l) for l in open("data/processed/xxx_test.jsonl", encoding="utf-8")]
tot = cov = 0
for r in rows:
    for k in r["gt"]:
        tot += 1
        cov += int(key(k) in {key(x) for x in ASKED})
print("真值字段总数=%d 被点名=%d ceiling=%.4f" % (tot, cov, cov / tot))
```

### 10.9 ⭐⭐ 「天花板达成率」才是跨档可比的量

换 prompt 后别只报新分数，把**每个档位的 recall 除以它自己那个天花板**：

| 档 | 3 字段（天花板 0.4168） | 8 字段（天花板 0.9907） | 变化 |
|---|---:|---:|---:|
| 2B 零样本 | 0.2302 → **55.2%** | 0.4961 → **50.1%** | −5.1pt |
| 2B SFT | 0.2084 → **50.0%** | 0.4184 → **42.2%** | −7.8pt |
| 商用 API | 0.3157 → **75.7%** | 0.7201 → **72.7%** | −3.0pt |

⇒ **同一档位换 prompt，达成率几乎不动；跨档位差异（50% vs 73%）才是真差距。**

> **「prompt 只决定天花板高度，能接近多少由模型能力决定。」**
> —— 这是本项目最可复用的一句结论，可直接引用。

**本地两档换 8 字段 prompt 的实测（同一批 100 条，唯一变量是 prompt）**：

| 档 | prompt | F1 | P | R | 幻觉率 |
|---|---|---:|---:|---:|---:|
| 2B 零样本 | 3 → 8 字段 | 0.3190 → **0.4691** | 0.5193 → **0.4449** | 0.2302 → **0.4961** | 0.16 → **0.59** |
| 2B SFT | 3 → 8 字段 | 0.2842 → **0.3752** | 0.4467 → **0.3401** | 0.2084 → **0.4184** | 0.28 → **0.73** |

**召回同样翻倍（约 2.1×，说明天花板对本地也存在），但精确率同时塌掉。**

机制：小模型把「找不到的字段可省略」这条**彻底忽略**，照着字段清单逐条填空、抽不出来就编：

| | 平均输出字段数 | 真值平均 | 幻觉键占输出 |
|---|---:|---:|---:|
| 商用 API | **6.6** | 6.43 | 4.6% |
| 2B 零样本 | **7.84** | 6.43 | 12.1% |
| 2B SFT | **8.00** | 6.43 | **19.3%** |

极值两格：`subtotal` 在 23 张本不存在的收据上被零样本编了 **23 次（100%）**；
`tax` 在 30 张上编了 27 次（**90%**）。

⇒ **错误形态从「该抽的没抽」变成「不该抽的也抽」** ——
缺的不是字段清单，是**「判断这张票据到底有没有这个字段」的能力，那是感知层。**

**必须同时做的三件事**：

1. **换 prompt 后不要直接把新分数填进原来的对比表。** 表里其他档位还是旧 prompt，
   混着填就变成反向的苹果比橘子。**保持该列同口径，另开一节写「prompt 修正后的数字」。**
2. **不要把一个档位的结论外推到其它档位。** 同一个天花板对强/弱模型的解释力完全不同：
   API 达 73–76%（有真实提升空间），本地只达 42–55%（补齐字段也补不回剩下那一半）。
   低分是 prompt 造成的还是感知造成的，**必须按档位分别跑、分别判断。**
3. **报「幻觉率」要看异常样本占比的分布，而不是只看均分。** 本例本地档的 0.59 / 0.73
   是**记录级**的（「输出了一个该样本 GT 里没有的键」），最能说明「照清单填空」这个行为。

### 10.10 追加的可选项：加强指令能压住幻觉吗？—— 不能

**设计**：新建 `prompt_manual_8f_strict.txt`（161 → **272 字符**，单行）。
与前版**只差一处**：把「找不到的字段可省略。」换成强规则段
（「只输出真实看到的字段 / 不存在就完全不输出该键名 / 不要 null 或占位符 / 严禁推测编造 / 宁缺毋滥」），
字段清单与输出格式句**逐字未动** ⇒ **干净的单变量对照**。

**结果**：

| 档 | prompt | F1 | P | R | 幻觉率 | tp | fp |
|---|---|---:|---:|---:|---:|---:|---:|
| ② 零样本 | 8 字段 | 0.4691 | 0.4449 | 0.4961 | 0.59 | 319 | 398 |
| ② 零样本 | ＋**强指令** | **0.4556** | 0.4344 | 0.4790 | **0.54** | 308（−11） | 401（**+3**） |
| ③ SFT | 8 字段 | 0.3752 | 0.3401 | 0.4184 | 0.73 | 269 | 522 |
| ③ SFT | ＋**强指令** | **0.3654** | 0.3333 | 0.4044 | **0.71** | 260（−9） | 520（−2） |

**幻觉率只降 2–5pt，F1 反掉 1pt 以上。**
关键是这组 tp/fp：**tp 掉了 9–11，而 fp 几乎没动**（398→401、522→520）
⇒ **强指令没有删掉任何一个编造字段，只劝退了本来抽对的字段。**

逐字段「无中生有」次数（真值里没这个键、模型却输出了）：

| 字段 | ② 基线→强指令 | ③ 基线→强指令 |
|---|---|---|
| subtotal | 23 → 20 | 23 → 23 |
| tax | 27 → 23 | 29 → **30（多编一个）** |
| total | 8 → 8 | 8 → 8 |
| store_addr | 15 → 14 | 19 → 19 |

平均输出键数也几乎不动（② 7.84→7.92、③ 8.00→8.00）。

⇒ **这就说明它压根没觉得自己在编。**
**模型不是「知道该省却硬要编」，而是真心认为那些字段就在图上。**
既然它「看到了」，「不存在就别输出」这句话对它**无从触发**。

**这是 §10.9 结论的第二次独立验证，和 DPO 的归因指向同一件事：
瓶颈在感知层，不在 prompt / 指令措辞层。**
**以后别再往 prompt 措辞方向找收益。**

**对外口径**：*「加强指令我试过，压不住 —— 幻觉率只掉 5 个点，F1 反而掉了 1 个点，
tp 掉 11 而 fp 涨了 3。因为小模型不是知道该省却硬编，它是真心以为图上有那些字段。
所以我把方向从 prompt 转向了分辨率、真实数据和字段级裁剪。」*
（这比「我加了个强指令把幻觉压住了」值钱得多。）

### 10.12 新增回归：`scripts/_test_evaluate_args.py`（13 项，纯 CPU 秒级）

**背景**：报告里给用户的命令报 `unrecognized arguments: --prompt-file` ——
该参数只加在 `evaluate_api.py` 上，**本地 `evaluate.py` 没有**。

**为什么容易漏**：项目里有**两个同族脚本**（本地 / API 各一个），
它们共享 `--tag / --limit / --mode / --data`，**看起来可以互换**。
新参数只加一边，另一边要等用户跑起来才暴露 —— 而这时用户已经在终端里等了。

**规矩**：

1. **给用户的命令，先在本地无副作用地跑一遍参数解析**：
   `python src/xxx.py --help` 核一遍新参数在不在。
2. **新参数加了一边，另一边也要加（或明确不支持）** ——
   最后两边都支持 `--prompt-file`，并补三条错误路径：
   `--prompt` / `--prompt-file` 互斥、文件不存在、两者都为空。
3. **长 prompt 一律走文件，不要走命令行**：换行、引号、反斜杠都会在 PowerShell 里被吃掉，
   而且 `--prompt "$(cat file)"` 这种写法在不同 shell 下行为不一致。
   加 `--prompt-file` 时顺手在运行头打印 `prompt 来源=文件 xxx.txt（161 字符）`，
   一眼能看出读对了没有。
4. **再补一个专门的参数回归脚本**（13 项），它断言：
   「两个脚本都暴露某参数」「共享参数两边都在（防漂移的通用断言）」
   「互斥 / 缺文件返回非 0」「运行头打印 prompt 来源」
   **「内置 flat prompt 必须仍是 3 字段」** ——
   **最后那条是口径防误改，比参数本身更值钱**：
   内置 prompt 一改，所有历史数字都失去可比性。

> **同族脚本的参数漂移是这类「最后一公里」故障的常见来源：
> 代码全对、结论全对，只有给用户的那条命令是错的。交付前核一遍命令，成本 10 秒。**

### 11.3 两个只有深挖才会发现的问题

**① 索引错位**

**有漏配行时就错位** ⇒ 高亮会标到错误的行，而且**不会报错**。
两个脚本各自都对，合起来才错。⇒ 新增 `remap_changed()` 换算。

**② 被测试逼出来的真实语义**

原本以为「模型多输出 schema 外的键（如 `备注`）」会显示成「多余」。
实际**完全不参与比对** —— `evaluate.flatten` 只遍历 schema 内字段，
所以多写一个键**既不算 TP 也不算 FP**。

Demo 必须与之保持一致（否则两套账），但要在面板上**显式提示**
「另有 schema 之外的键未参与比对」。
⇒ **「多余（紫）」的真实语义是：GT 该字段为空、模型填了值。**

## 13 踩坑总表（按类别索引）

### A 类：静默失败 —— **本项目最值钱的一类坑**

共同特征：**失败被伪装成一个看起来正常的结果**。不崩、不报错、指标只是变难看一点。

| # | 坑 | 症状 | 真因 | 处置 |
|---|---|---|---|---|
| A1 | 空响应被当有效结果 | 同域 F1 从 0.9546 **悄悄掉到 0.8622**，102 条里 16 条中招 | `content or ""` + 从不检查 `finish_reason` | 空响应 / `length` → 退避重试；**续跑缓存拒绝空响应**（否则瞬时故障被永久固化） |
| A2 | `load_dotenv()` 定义了没接线 | 「明明把 key 填进 `.env`，仍报环境变量未设置」 | 函数写好了，`main()` 里**从未调用** | `main()` 顶部调用 + **monkeypatch 断言 `main()` 调用过它** |
| A3 | 余额耗尽被降级成「优化无效」 | GEPA **退出码 0**、`Δ +0.0000`，实际 396 次调用全失败 | 无 preflight、无结果自检 | **preflight 秒退（rc1）+ 结果自检（rc2）**；区分「没跑成」与「优化无效」 |
| A4 | `disable_adapter()` 失效 | 界面**安静显示四份相同结果** | 唯一无法 CPU 验证的环节 | `--smoke`：断言两档输出不同 |
| A5 | `set_adapter("ref")` 失效 | loss 曲线**看起来完全正常**，但 ref 跟着策略一起漂移，**整个实验作废** | ln2 自检在切换失效时**同样通过** | **扰动 ref 权重**看结果是否变化（+ 反例对照组） |
| A6 | `hash(prompt)` 跨进程不稳定 | 每次重跑都判「配置漂移」→ 旧代码 `unlink()` → **30 分钟推理当场蒸发** | CPython 随机化 str 哈希种子 | `md5` 摘要 + **不匹配时改名保留，永不 unlink** + 换 seed 的子进程测试 |
| A7 | 打分崩了毁掉推理结果 | 推理 102/102 完成（29.9 分钟）后 `AttributeError` → 整批作废 | 打分层无类型防御、与推理耦合 | `_as_dict`/`_as_rows` + 每样本 try/except + `--score-only` |
| A8 | 索引口径错位 | 高亮标到错误的行，**不报错** | 后处理用「预测行下标」，打分用「配对后槽位」 | 显式换算函数 `remap_changed()` |

> **通用判据：指标突然变难看时，先查数据管道，再下模型结论。**
> 查管道的第一步：**看非法 / 失败样本的预测长度分布** —— 一串 0 或半截长度就是管道故障。
> A1 那条如果直接抄下 0.8622，结论会变成「商用 API 全面不如本地小模型」。**完全站不住。**
>
> **通用原则：任何「优化器 / 搜索器」跑完后，都要问一句「它的输出真的变了么？」**
> 没变就不是「无提升」，是「没跑成」。

## 14 结论清单（可复述 / 可讲述）

### 14.1 九条技术结论

1. **同域上，本地 2B 微调（0.9782）略高于商用 API（0.9681，关思考）**，差距 1.0pt，
   措辞是「略高 / 基本打平」——**闭集字段 + 固定版式的任务上，微调把版面与词表都内化了，
   大模型不带这个领域先验。**
2. **跨域反过来（0.4408 > 0.3190 > 0.2842），但三档都没上 0.5**
   ⇒ 这个任务的瓶颈是**领域适配**，不是模型规模。
3. **知识注入的收益与基座能力成反比**：+0.0522（2B 零样本）/ +0.0109（API）/ −0.0003（SFT）。
   三点连成单调曲线 ⇒ **做后处理类改进前，先确认基座确实没有这个能力。**
   反向看，这条曲线本身就是「微调买到了什么」的强证据。
4. **天花板达成率几乎只随模型变**：② 55.2%→50.1%、③ 50.0%→42.2%、⑤ 75.7%→72.7%。
   ⇒ **prompt 只决定天花板高度，能接近多少由模型能力决定。**
5. **瓶颈在感知层，不在决策层** —— 两条独立证据指向同一结论：
   - **DPO 负结果**：加分辨率把错误砍 78%，DPO 是 0%（DPO 只重分配概率，不增加信息）
   - **强指令压不住幻觉**：幻觉率只降 2–5pt，F1 反掉 1pt，**tp 掉 9–11 而 fp 几乎不动**
     ⇒ 它不是「知道该省却硬编」，是**真心认为那些字段在图上**
6. **分辨率 > 数据量**：384→768px 涨 1.7pt；数据量砍到 25% 只掉 1.2pt。
   文档抽取任务**先调分辨率**。
7. **自动 prompt 优化的第一价值是「诊断」，不是「优化」** ——
   GEPA 找出了「字段清单缺失」这个结构性问题（+26.8pt），但它自己写的措辞规则是**负贡献**（−2.6pt）。
8. **评测 prompt 的口径可以人为压低上限** —— 报跨域指标前必须算 recall 天花板，
   否则会把「口径缺陷」误读成「模型不行」。
9. **SFT 买到的主要能力是「读写中文字段」，不是「认数字」** ——
   零样本在中文表头文本上错 80–88%（供应商 87.8% / 项目名称 80.6%），
   而错例形如 `沣西市政道路改造工程 → 洋市市政道路改造工程`，
   **不是读不清，是语言先验在编像样的中文名词。**

### 14.2 三份各有价值的「负结果」

| 负结果 | 为什么比正结果值钱 |
|---|---|
| DPO 无效 | 「验证了方法无效 + 三层定位根因（chosen 质量 / 感知层瓶颈 / 域异分布）」比提 0.3 个点更体现判断力 |
| GEPA 措辞规则负贡献 | 三组归因对照把「自动优化的功劳」拆干净了 —— 这类实验做得少 |
| 强指令压不住幻觉 | 第二次独立验证「瓶颈在感知层」，且给出了 tp/fp 的机制解释 |

### 14.3 一句可背的自述

> 我在单张 8GB 显卡上微调 Qwen3-VL-2B 做工程材料清单的结构化提取，
> 同域字段级 F1 做到 0.9782，比商用 API 略高。做的过程中最有价值的不是这几个点，
> 而是几条量化结论：**知识注入的收益与基座能力成反比**；**prompt 只决定天花板高度，
> 能接近多少由模型能力决定**；以及 **DPO 和加强指令都压不住幻觉，因为瓶颈在感知层**——
> 同一批错误用提高分辨率能砍掉 78%，用 DPO 是 0%。

## 15 如果重来一次

### 15.1 会提前做的事

| # | 做法 | 省下的东西 |
|---|---|---|
| 1 | **第一天就把「静默失败」当成一类缺陷来设计**（所有外部调用都检查返回、所有关键产物都自检） | A1–A6 六个坑，其中一个（A6）差点毁掉 30 分钟推理 |
| 2 | **写任何对照实验前先算口径上限**（召回天花板那 30 秒的检查） | 避免「跨域 0.44 说明模型不行」这个错结论，以及后面一整轮 prompt 方向的探索 |
| 3 | **把「训练脚本的数学写成纯函数 + import 放 main()」当成硬规范** | DPO 的 off-by-one 是最贵的 bug 类型；这次做对了，应该更早、更彻底 |
| 4 | **参数回归早期就建**（同族脚本参数漂移） | 用户白等一轮 + 一条错命令 |
| 5 | **不要往 prompt 措辞方向花时间** | 强指令那条实验（虽然值得做，因为它是**证据**而不是**尝试**） |

### 15.2 会改的设计

1. **合成数据的字段设计**：供应商 / 编号应该**有规律可循**（真实场景就是那样），
   不该做成逐条随机 —— 否则这两个字段退化成「纯 OCR 测试」，**夸大了感知难度**，
   也让「知识注入」在这两个字段上的判断变得更绕。
2. **评测 prompt 一开始就写全字段**（8 个），把 3 字段版本当成一个**显式的对照臂**而不是默认值。
   这样跨域的四档（3 字段 / 8 字段 / 加强指令 / 本地对照）从一开始就是设计好的，
   而不是后来逐个补做。
3. **偏好数据的目标域**：如果目标是压跨域幻觉，偏好数据就应该**包含跨域样本** ——
   143/143 全是同域合成，方法层面就不成立。
4. **更早引入 API 档**：⑤ 档不只是「上界」，它还是**判断本地瓶颈在哪的参照系**
   （有了它才知道 75.7% vs 50.1% 这个差距意味着什么）。

### 15.4 最后一条：这个项目真正的资产是什么

不是 0.9782 这个数字，也不是 8GB 显卡上跑通 QLoRA 这件事本身。是**下面这三样**：

1. **一条完整可复用的工程范式**：
   「多档对照 → 失败分析 → 定位瓶颈层 → 针对性改进 → 再验证」，
   而且每一环都有可量化的证据（消融 6 档 / 错误结构 / 三层根因 / 达成率曲线）。
